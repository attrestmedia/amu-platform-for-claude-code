> **이 문서의 지위**: AMU 콘텐츠 성과의 해석 규칙과 Winning Pattern 학습 체계의 단일 기준.

* 문서 버전: `content-intelligence-v2.7`

## 1. 핵심 원칙

1. **평균을 핵심 체력 지표로 쓰지 않는다.**
2. 콘텐츠 성과는 **Attention → Relationship → Business** 세 축으로 나눈다.
3. 콘텐츠 역할이 다르면 같은 지표로 승자를 정하지 않는다.
4. 상위 콘텐츠는 그대로 복사하지 않고 **문법을 분해해 재실험**한다.
5. 제작비와 시간을 성과와 함께 본다.
6. 분석은 보고로 끝내지 않고 Marketing Oops의 Next Action으로 연결한다.
7. 반복 방문 장치는 콘텐츠 자체의 호기심·놀라움·근거·참여·보상·실용성·기억·연속성을 대신하지 않는다.

## 13. Discovery Layer (신설 2026-08-24)

> **SEO는 이미 질문이 있는 사람을 잡고, Discovery 콘텐츠는 질문이 없던 사람에게 질문을 만든다.**

| Layer | 대상 | 산출물 | 성과축 |
| --- | --- | --- | --- |
| Search | 이미 검색하는 사람 | Pillar/Cluster·검색 콘텐츠 | GSC 노출·Verified Reach |
| Discovery | 질문이 없던 사람 | Question Hook·Shorts·Threads·Instagram | Attention → Magazine 유입 |
| Relationship | 관계를 잇고 싶은 사람 | Save·Follow·Continue·Related·Newsletter | Relationship·Return |

세 Layer는 경쟁 관계가 아니다. Search는 질문이 있는 사람을, Discovery는 질문이 없던 사람에게 질문을 만든다. 양쪽 모두 Magazine으로 수렴한다.

## 14. Question-Discovery Format (Question-first)

콘텐츠 후보를 만들 때 **기사(답)부터 시작하지 않는다.** 사람이 그냥 지나칠 수 없는 질문을 먼저 발견한다.

### 후보 발굴 흐름

```text
기존(Article-first)
전문 주제 → 글 작성 → 제목 → SNS 배포

변경(Question-first)
사람이 궁금해할 현상 → 질문 설계 → 핵심 원리
→ 짧은 콘텐츠 → Magazine 심화 → 관련 콘텐츠
```

### 6단계 구조

```text
Stage 1. Familiar      익숙한 대상을 고른다 (ChatGPT·쿠팡·배달앱·월급·광고 등)
Stage 2. Contradiction 상식과 충돌하는 사실을 찾는다
Stage 3. Question      충돌을 "왜/어떻게" 질문으로 바꾼다 (제목이 답을 주면 안 됨)
Stage 4. Mechanism     원인 → 작동 원리를 설명한다 (전문 용어는 여기서 첫 사용)
Stage 5. Resolution    "아, 그래서 그런 거구나" 하나의 이해를 남긴다
Stage 6. Expansion     더 알고 싶은 사람만 Magazine으로 이어진다
```

### 원칙

- 제목(질문)은 세게, 답은 그보다 강해야 한다: `Hook Strength ≤ Answer Strength`
- 전문 지식을 대중이 지나칠 수 없는 질문으로 번역한다. **지식은 그대로, 입구만 바꾼다.**

## 15. Discovery Packet (1 Idea → 다중 표면 → 1 Magazine Hub)

성과 가능성이 높은 콘텐츠는 기사 1건으로 끝내지 않는다.

```text
1 Idea
→ Main Article (Magazine Hub)
→ Short (모순 → 원인 → 메커니즘 → Magazine 연결)
→ Threads (관찰 → 의외의 사실 → 짧은 해석)
→ Instagram (Before/After·데이터 시각화 증거)
→ Related Articles (Cluster)
```

- 모든 채널을 의무적으로 만들지 않는다. 채널 적합도 게이트(Pre-Fit) 통과분만 제작한다.
- Shorts/Reels는 **시각화 가치**(현상을 영상으로 보여줄 수 있고 원리가 시각적으로 이해되는 경우)에만 적용한다.
- 동일 본문 복제가 아니라 채널 역할에 맞춘 재구성이다.

## 16. Discovery 후보 7문항 평가

새 Discovery 콘텐츠 전에 7문항을 평가한다.

| 평가 | 질문 |
| --- | --- |
| Familiarity | 사람들이 이미 아는 대상인가 |
| Surprise | 예상과 다른 사실이 있는가 |
| Question | 한 문장 질문으로 만들 수 있는가 |
| Mechanism | 설명할 흥미로운 원리가 있는가 |
| Visual | 시각화할 수 있는가 |
| Utility | 알고 나면 실제 도움이 되는가 |
| Cluster | 기존 AMU 콘텐츠와 연결되는가 |

```text
6~7개 → 강력한 Discovery 후보
4~5개 → Magazine / 검색 콘텐츠
0~3개 → 우선순위 하향
```

Magnetism Score(발행 전 예측)와 결합해 운영한다.

## 17. Discovery KPI Funnel

```text
Discovery Impression
→ View / 3s hold
→ Profile·Link Visit
→ Magazine Entry
→ Article Consumption (60s+ / 2건+)
→ Related Article
→ Save / Follow / Continue
```

### 기록 차원 (Hook Intelligence 확장)

각 Discovery 콘텐츠에 다음을 기록한다:

```text
Topic / Hook Type / Contradiction Type / Question Type / Visual Type
/ Length / Channel / View / CTR / Completion / Share / Save
/ Magazine Entry / Relationship Action / Return
```

100건 내외가 쌓이면 AMU 독자가 어떤 질문에서 멈추는지 알 수 있고, Marketing Oops가 승자 포맷을 확대한다.

## 18. Discovery 가드레일

- **클릭베이트화 금지**: `Hook Strength ≤ Answer Strength`. 질문이 강한데 답이 약하면 신뢰가 무너진다.
- **AI 영상 공장화 금지**: AI의 역할은 제작 자동화가 아니라 **시각화**다. 좋은 질문 없는 AI 영상은 비싼 노이즈다.
- **모든 콘텐츠 Shorts화 금지**: 영상 설명 가치가 없는 콘텐츠는 Magazine/Threads에 남긴다.
- **Discovery 단계 제품 CTA 남용 금지**: 관계 행동(Save·Follow·Continue·Related·Newsletter)이 먼저다.
- **검증되지 않은 숫자 훅 금지**: 실제 데이터·공식 통계·신뢰 가능한 연구·AMU Observed Data·Validated Proof만 사용.
- 특정 외부 계정의 Hook을 AMU의 영구 규칙으로 복사하지 않는다(§7 원칙 유지).

## 19. Question-Driven Content (Question DNA · Question Loop, 신설 2026-08-24)

> **좋은 콘텐츠는 답을 많이 담은 콘텐츠가 아니라, 좋은 질문을 만들고 독자가 그 답을 끝까지 따라가게 만드는 콘텐츠다.**

Discovery(§13~§18)가 **입구(Reach)**를 질문으로 만든다면, Question-Driven은 **본문(Consumption·Relationship)**을 질문의 연쇄로 만든다.

### Question DNA (작성 전 4요소)

```text
Who      이 문제를 실제로 겪는 사람
Desire   그 사람이 궁극적으로 얻으려는 결과
Obstacle 무엇이 그것을 막고 있는가
Question 그래서 어떤 질문이 생기는가
```

### Question Loop (본문 전개 8단계)

```text
Desire → Obstacle → Tension → Question
→ Reveal → Next Question → Resolution → Action
```

핵심은 답을 숨기는 것이 아니라 **답을 주면서 다음 질문을 만드는 것**이다.

### 채널 적용

| 채널 | 적용 |
| --- | --- |
| 검색 | Search Intent 우선 + 명확한 대상 + Question Gap |
| Threads | 스레드 자체를 Question Loop로(`관찰 → 의외 → 질문 → 기준 → 다음 질문`) |
| LinkedIn | 질문을 대표 관점·산업 변화에 연결 |
| Newsletter | `이번 주 질문 → 부분 해답 → 새 문제 → 다음 호 질문`(연속성) |
| Magazine→확장 | CTA를 "기사 질문의 연속선"으로(예: "내 상황에도 적용되는지 물어보기") — 모든 글에 강제 금지 |

## 20. Tension Taxonomy (긴장의 종류, 신설 2026-08-24)

공포·분노·FOMO를 과도하게 쓰지 않는다. 의미 있는 긴장(Tension)을 만든다.

### 권장 Tension (6종)

| Tension | 구조 | 예 |
| --- | --- | --- |
| Expectation Gap | 예상 vs 현실 | AI를 도입했는데 생산성이 안 오른다 |
| Contradiction | 양립하기 어려운 두 사실 | 제품은 잘 팔리는데 주가가 떨어진다 |
| Hidden Cause | 겉 이유 ≠ 실제 원인 | 트래픽은 늘었는데 사업이 안 자란다 |
| Trade-off | 어느 쪽도 비용 존재 | SEO를 위해 많이 쓰는 게 오히려 SEO를 망친다 |
| Change | 과거의 방식이 더 이상 안 통함 | AI가 잘 쓸수록 글쓰기만으론 차별화 어렵다 |
| Unresolved Outcome | 결과 미결정 | 금리 인하 예상인데 자산 가격은 안 움직인다 |

### 숫자를 장면으로

```text
숫자 → 의미 → 상황 → 질문
```

> 공장은 24시간 돌아간다. 제품은 품절될 정도로 팔린다. 그런데 주가는 떨어진다. 왜?

### 금지 Tension (클릭베이트 변질 방지)

```text
근거 없는 공포 / 과장된 위기 / 존재하지 않는 갈등
/ 핵심 답 과도한 숨김 / 사실보다 강한 제목
/ 검증되지 않은 숫자 / 분노·혐오로 체류 확보
```

## 21. Question-Driven 평가·판정·실패 (신설 2026-08-24)

### 평가 7요소 (기존 Magnetism에 통합)

별도 거대 시스템을 만들지 않는다.

| 요소 | 평가 질문 |
| --- | --- |
| Desire | 독자가 원하는 결과가 보이는가 |
| Obstacle | 막는 문제가 명확한가 |
| Stakes | 이 문제가 왜 중요한지 알 수 있는가 |
| Tension | 기대와 현실의 의미 있는 차이가 있는가 |
| Question | 독자가 자연스럽게 질문하게 되는가 |
| Progression | 질문과 답이 단계적으로 발전하는가 |
| Resolution | 최초 질문에 충분한 답을 제공하는가 |

### A/B 가설

> 정보형 Hook보다 Desire + Obstacle + Question 구조의 Hook이 Consumption·Relationship을 높인다.

| 안 | 예 |
| --- | --- |
| A(Information) | OpenAI가 새로운 AI 에이전트 기능을 발표했다 |
| B(Question) | AI가 일을 대신해주는 도구는 늘어나는데 왜 업무시간은 줄지 않을까 |

### 성공 판단 (CTR 단독 최적화 금지)

```text
1차 CTR
2차 60초 소비·스크롤 깊이·2건 이상 소비
3차 저장·공유·팔로우·관련 글 클릭
4차 Return
```

### 실패 패턴

1. 모든 콘텐츠를 질문형 제목으로 패턴화(질문의 핵심은 `?`가 아니라 인지적 긴장)
2. 질문만 강하고 답이 약함(= 클릭베이트)
3. 답을 과도하게 숨김(필요한 답을 주며 더 깊은 질문으로 이동)
4. 감정을 공포·분노로만 이해(우선 감정: 호기심·놀라움·공감·기대·발견·이해의 쾌감)
5. SEO 검색 의도 희생(검색 콘텐츠는 정확한 문제 해결 우선)

## 22. Content Experience System (신설 2026-08-26)

> **모든 콘텐츠를 고비용 인터랙티브 기사로 만들지 않는다. 대신 모든 콘텐츠를 고가치 콘텐츠로 승격할 수 있는 구조로 만든다.**

신규 기사와 리뉴얼 기사는 다음 공통 문법으로 설계한다. 다만 이는 모든 기사에 일곱 개의 섹션이나 같은 순서를 강제한다는 뜻이 아니다.

```text
Question → Evidence → Tension → Discovery
→ Experience → Application → Next Question
```

`Experience`는 개발된 UI를 뜻하지 않는다. E1에서는 독자가 잠깐 선택·비교·예측한 뒤 답을 확인하는 정적 장면도 유효하다. 성과와 사업 적합성이 확인된 기사만 같은 자리를 재사용 가능한 모듈로 승격한다.

### 7단 문법의 독자 심리 계약

이 문법은 소제목 순서·질문형 제목·단골 reveal 문구를 강제하는 템플릿이 아니다. 각 단계가 아래 독자 경험을 만들어야 한다.

| 단계 | 독자 심리 기능 | 통과 기준 |
| --- | --- | --- |
| Question | ‘왜 지금 읽어야 하지?’에 답한다 | 실제 욕구·장애에서 나온 한 문장 질문 |
| Evidence | ‘믿고 따라가도 되는가?’에 답한다 | 설명보다 먼저 만나는 관찰·자료·사례와 출처·한계 |
| Tension | 계속 읽을 인지적 마찰을 만든다 | 합리적 기대와 검증된 현실의 실제 충돌 |
| Discovery | 이해의 쾌감을 준다 | 근거가 바꾼 판단을 명료하게 해석 |
| Experience | 내 판단을 시험할 기회를 준다 | `판단 대상 → 판단할 틈 → reveal`이 모두 있음 |
| Application | 내 상황으로 옮길 길을 준다 | 조건·한계를 갖춘 행동·판단 기준 |
| Next Question | 답 이후에도 읽을 이유를 남긴다 | 관련 글 나열이 아닌, 답이 낳은 실제 다음 호기심 |

- `Hook Strength ≤ Answer Strength`: 제목·훅보다 약한 답이나 근거는 통과하지 못한다.
- Evidence 없는 반전, 존재하지 않는 갈등, 핵심 답의 과도한 은닉은 Tension이 아니다.
- ‘3초 생각’, ‘정답은’, ‘하지만’ 같은 고정 장치나 모든 H2 질문형으로 이 문법을 반복 생산하지 않는다. 문장 모양이 아니라 근거와 독자 경험이 기준이다.

### Cold Open (신설 2026-08-28)

7단 문법의 `Question`은 **어디서 시작하는지**까지 규정하지 않았다. 그 결과 도입부가 정의문으로 열리는 기사가 반복됐다.

첫 3~5문장 안에 아래 셋이 모두 있어야 한다. 순서는 자유다.

| 요소 | 뜻 |
| --- | --- |
| 문제 | 독자가 지금 겪고 있는 상태 |
| 장면 | 그 문제가 드러나는 구체적인 순간이나 대상 |
| 긴장 | 합리적 기대와 실제가 어긋나는 지점 |

- 배경 설명·용어 정의·시장 규모로 열지 않는다. 그건 Evidence가 할 일이다.
- 첫 문장에 키프레이즈를 넣는 SEO 요구와 충돌하지 않는다. 장면 안에 자연스럽게 넣는다.
- `coldOpen` 메타에 이 셋을 한 줄씩 적는다. 적히지 않으면 도입부가 설계되지 않은 것이다.

### 최소 구성과 선택적 강화

- **모든 E1 필수**: `Primary Question`, `Evidence`, `Tension 또는 Discovery`, `Application/Payoff`.
- **강하게 권장**: `Assumption`, 정적 `Experience`, `Memorable Insight`, `Next Question`.
- **필요할 때만**: `Trust/Limit`, E2/E3 모듈, 서비스 확장.
- 짧은 뉴스·Utility 글은 권장 요소를 억지로 늘리지 않는다. 대신 생략한 이유를 품질 근거에 기록한다.
- **WP → WP 리뉴얼은 예외적으로 9축 전부가 필수**다. 기존 글을 교체할 만큼 충분한 새 가치가 없으면 발행하지 않는다.
- WP → WP 리뉴얼의 기존 이미지 asset은 글의 편집 계승값이 아니다. writer·quality reviewer에게 공개하지 않고, 두 검토 뒤 컨트롤러가 권리·최신성·새 `freshImageBrief` 및 본문 사실 적합성을 확인한 경우에만 재활용한다. ALT·캡션·배치는 새 본문 기준으로 다시 정하고 최종 패키지 independence 검토를 거친다.

### 9축 콘텐츠 품질 게이트

모든 기사 품질 게이트는 아래 9축을 **본문 안의 위치와 근거**로 평가한다. 라벨·점수만 적은 평가표는 미통과다. 일반 기사는 권장 요소를 생략할 때 `not_applicable`과 기사 유형에 따른 이유를 기록할 수 있지만, WP → WP 리뉴얼은 9축 전부에 구체 근거가 있어야 한다.

| 축 | 검증 질문 |
| --- | --- |
| Curiosity | 독자의 실제 질문을 여는가 |
| Surprise | 합리적 예상과 다른 검증된 발견이 있는가 |
| Evidence | 관찰·자료가 설명보다 먼저 제시되는가 |
| Participation | 독자가 답 전에 판단할 틈이 있는가 |
| Payoff | 최초 질문에 훅보다 강한 답을 주는가 |
| Utility | 조건·한계를 포함한 적용 기준이 있는가 |
| Memorability | 독자가 자기 말로 다시 꺼낼 발견이 있는가 |
| Continuation | 답 뒤에 실제 다음 호기심이 생기는가 |
| Voice | 독자에게 보이는 문장이 사람의 말인가 |

**Voice 축은 2026-08-28에 신설했다.** 기존 8축은 콘텐츠의 실질만 봤고 독자에게 보이는 문장의 말맛을 보는 축이 없었다.
2026-08-28 리뉴얼 실측에서 그 8축은 법령 오귀속을 차단했지만, 연구 계획서처럼 읽히는 `primaryQuestion`은
Curiosity 축을 통과했다. Curiosity는 "질문이 열리는가"를 보지 "사람이 그렇게 말하는가"를 보지 않기 때문이다.

Voice가 보는 것은 **독자 표면에 노출되는 문장**이다 — `title`, H2, `primaryQuestion`, `coldOpen`, `heroLine`,
확장 경험 문구. 근거 문단의 정밀한 표현은 대상이 아니다.

| Voice 통과 기준 | 실패 신호 |
| --- | --- |
| 소리 내어 읽었을 때 사람이 하는 말로 들린다 | 한 문장에 조건절·병렬 명사구가 세 개 이상 쌓여 있다 |
| 판단과 근거는 그대로 두고 독자를 부르는 문장만 사람 말이다 | 정의·범위·예외를 한 문장에 다 넣었다 |
| 내부 설계 언어가 화면 문자열로 새어 나오지 않는다 | `Article Experience`·`E1/E2/E3` 같은 용어가 독자에게 보인다 |

> **App 경험형 기사(node-app `/magazine/{slug}`)는 같은 9축을 쓰되 가중치가 다르다 (2026-09-09).**
> **두 표면은 성공 정의가 다르다** — 매거진은 검색 유입과 지식 재사용(Intelligence)이 핵심이고,
> App 경험형 기사는 독자가 실제로 흥미를 느끼고 끝까지 체험했는가가 목적이다.
> 그 표면에서는 Curiosity·Surprise·Participation·Continuation이 **차단축**, Utility는 **완화축**이고,
> 1차 품질 기준이 "좋은 정보인가"가 아니라 **"다음 화면을 넘기고 싶은가"**다.
> **매거진의 SEO 게이트는 App 표면의 품질·발행 조건이 아니며, 표현 강도 제약도 사실성 기준으로만 건다.**
> 축의 정의는 이 절이 소유하고, **App 표면의 가중치·공개 시점·표현 강도·긴장 유지 규칙의 정본은
> `.claude/refs/content-policy/app_post_draft.md` §5**다. 여기서 복제하지 않는다.
> 매거진 표면(WordPress)의 기준은 바뀌지 않는다.

### 제작 순서

```text
Research
→ Curiosity Design
→ Story / Episode Design
→ Article Generation
→ Performance Review
→ Experience Upgrade
```

> 여기서 `Story / Episode Design`은 **기사 본문**의 섹션(Section Episode) 설계다. 독립 Interactive Story(ISCS)의 기획·제작 규약은 `INTERACTIVE-NARRATIVE-STANDARD.md`가 소유하며, Magazine 기사는 그 Story의 선택적 Intelligence 원천(`sourceRefs`)으로만 쓰인다.

일반적인 `주제 → 서론 → 정보 나열 → 결론 → CTA` 순서로 바로 본문을 생성하지 않는다.

| Level | 이름 | 구성 | 기본 용도 |
| --- | --- | --- | --- |
| E1 | Story | Question·Evidence·Discovery·정적 Experience·Application | 모든 일반 신규 기사 |
| E2 | Enhanced | E1 + 비교·퀴즈·체크리스트·타임라인·정적 시각화 | 검색·소비 반응이 확인된 핵심 기사 |
| E3 | Interactive | E2 + 사용자 입력·생성·진단·계산·시뮬레이션·맥락형 서비스 | PMF 후보·Pillar·전략적 Reference Implementation |

### 기본값과 예외

- 신규 기사의 기본값은 E1이다. E1부터 `Experience Slot`과 `Next Question`을 내부 메타로 예약한다.
- E2·E3는 슬롯을 모듈로 바꾸는 `Experience Upgrade`다. 같은 WP URL의 콘텐츠 리뉴얼과는 별도 작업이며, WP → WP 리뉴얼이 요청되면 `content_production_workflow.md` “WP → WP 같은 URL 리뉴얼 절차”의 전면 재작성 교체 규칙이 우선한다.
- `Search Demand + Consumption + Relationship + Business Fit`을 함께 보고 승격한다. 발행량·단순 조회수·서비스 클릭만으로 승격하지 않는다.
- 반응이 약하거나 제작비 대비 가치가 낮은 글은 E1에서 끝낸다. 모든 글을 강제로 승격하지 않는다.
- 전략적 첫 사례는 실측 전에도 E3 파일럿이 될 수 있다. 이때 `PMF 검증 후보`로만 표기하고 PMF가 증명됐다고 주장하지 않는다.
- 한 번의 승격 실험에서는 Primary interaction 하나만 바꾼다. 효과 판정 전에 본문·카피·모듈·CTA를 동시에 대수술하지 않는다.

## 24. Article Archetype과 Curiosity Engine

기사마다 **Primary Archetype 1개**를 고른다. 보조 Archetype은 1개까지 허용하되 본문 구조를 지배하지 않는다.

| Archetype | 기본 흐름 | 주 사용처 |
| --- | --- | --- |
| `make` | 결과 → 원리 → 선택 → 생성 → 검수 → 개선 | AI Creatives·Services |
| `experiment` | 질문 → 실험 → 결과 → 원리 → 적용 | AI·생산성·심리 |
| `mystery` | 이상 현상 → 단서 → 원인 → 연결 → 영향 | 경제·기술·마케팅 |
| `decision` | 상황 → 선택 → 결과 → 이유 → 판단 기준 | 비즈니스·스타트업·투자 |
| `teardown` | 결과물 → 오류 찾기 → 해부 → 개선 → 비교 | 마케팅·AI·비즈니스 |
| `simulator` | 변수 변경 → 결과 변화 → 원리 → 한계 | 경제·투자·생산성 |
| `build` | 목표 → 예상 → 실제 증거 → 실패 → 판단 → 변경 → 결과 | AMU Stories |

각 핵심 섹션은 아래 Curiosity Type 중 하나를 사용해 작은 Episode로 설계한다.

```text
mystery / contradiction / comparison / prediction
/ detection / decision / reveal
```

질문형 문장 부호를 강제하지 않는다. 중요한 것은 `?`가 아니라 Evidence와 Tension으로 답할 수 있는 인지적 긴장이다.

## 25. Episode·Interaction Slot·콘텐츠 메타 계약

H2/H3는 정보 분류명이 아니라 `질문 → 단서/관찰 → 발견/판단`이 완결되는 Episode로 설계한다. 각 Episode는 Threads·Instagram·Shorts·Newsletter snippet 후보가 될 수 있어야 하지만, 채널 산출은 Pre-Fit을 통과한 경우에만 만든다. 시리즈 형식의 연결 글도 제목과 본문은 하나의 주제를 가진 하나의 완전한 글이어야 하며, 다른 편 없이 `primaryQuestion`의 답·근거·적용 기준이 완결돼야 한다.

신규·리뉴얼 기사 brief에는 최소한 다음 메타를 남긴다.

```text
contentRole
primaryArchetype
supportingArchetype(optional)
experienceLevel
primaryQuestion
thesis
memorableInsight
nextQuestion
questionDNA { who, desire, obstacle, question }
episodes[] { sectionId, curiosityType }                                            ← App 경험형 기사 전용
interactionSlots[] { slotId, sectionId, intent, staticFallback, candidateModule }   ← App 경험형 기사 전용
expansion { service, contextKey, entrySectionId, returnSectionId } (optional)
qualityEvidence { curiosity, surprise, evidence, participation, payoff, utility, memorability, continuation, voice }
```

**매거진 `knowledge` 기사는 여기에 지식 계층 메타를 더한다** — `thesis`·`intelligenceRole`·`evergreenPrinciple`·`temporalClaims[]`·`conditions[]`·`limitations[]`·`counterExamples[]`·`entities[]`·`topics[]`·`intent`·`audience`·`knowledgeUnits[]`·`intelligence`. **필드명의 정본은 node-app 저장 계약**(`magazine_knowledge_articles`·`magazine_knowledge_units`)이며 목록과 작성 주체는 `.claude/refs/content-policy/magazine_knowledge_article.md` §28이 소유한다. 여기서 복제하지 않는다.

**`episodes[]`·`interactionSlots[]`는 App 경험형 기사 전용이다 (2026-09-04).** 순수 매거진 기사는 구조화 `body[]`가 없고 본문이 마크다운 산문이라 `sectionId`가 대응할 앵커가 존재하지 않으며(실측: 리뉴얼 초안 5건 전부 `<h2>` 0개), `curiosityType`은 WordPress·`magazine_knowledge_articles` 어느 저장 계약에도 없다. 매거진 기사는 두 필드를 남기지 않고, Episode 설계는 소제목과 `qualityEvidence`로 확인한다. App 경험형 기사에서는 node-app `appContentValidate`가 `body[].sectionId ↔ episodes[].sectionId` 1:1을 실제로 강제하므로 필수다. 종전 `episodes[]`의 `question`·`evidence`·`discovery`·`application`·`assumption`·`reveal` 6필드는 소비자가 없어 함께 폐기했다 — 근거: `.agent/docs/project/2026/09/20260904_220354__episodes-meta-deprecation-and-storage-readiness.md`

`memorableInsight`는 결론 요약이 아니라 독자가 자기 언어로 다시 꺼낼 하나의 발견이다. `nextQuestion`은 관련 콘텐츠 링크나 CTA가 아니라, 답을 얻은 뒤 새로 생기는 미해결 호기심이다. `qualityEvidence`는 각 축의 점수가 아니라 실제 본문 위치·출처·판단 지점을 적는다. 일반 기사에서 권장 요소를 생략하면 `not_applicable`과 이유를 함께 적는다.

### Assumption → Evidence → Reveal (2026-08-27 신설, 2026-09-04 개정 — 본문 설계 사고법)

아래 다섯 항목은 Episode 본문을 설계하는 사고 순서이며 **출력 메타 필드가 아니다.** 설계 결과는 본문과 `qualityEvidence`로 확인한다.

`assumption`은 **독자가 자연스럽게 예상하는 답**이다. Tension·Mystery·Prediction처럼 예상이 뒤집히는 Episode에서 필수이며, 단순 Utility·정의·절차 Episode에는 억지로 만들지 않는다.

```text
question     독자가 품는 질문
evidence     관찰·데이터·사례
discovery    근거를 해석해 얻은 발견
application  그래서 독자는 무엇을 다르게 하는가
assumption   선택: 독자가 예상하는 합리적 답
reveal       선택: evidence가 assumption을 뒤집어 드러낸 실제 설명
```

`curiosityType`은 **Episode 단위로 지정한다.** 기사 전체에 한 묶음(`curiosityTypes[]`)으로만 선언하면 개별 섹션이 평범한 설명문으로 회귀하고, 생성 단계에서 "이 Episode는 mystery인데 첫 문단부터 정답을 말하고 있다" 같은 자동 검수가 불가능해진다. 단, 모든 Episode를 반전형으로 만들지 않는다. Article Archetype과 해당 섹션의 기능이 Episode 모양을 결정한다.

### Slot 원칙

- **정적 블록은 승격 대상 모듈의 모양으로 쓴다.** `candidateModule`은 현재 구현 예정 모듈(`quiz` · `reveal` · `compare` · `checklist` — 로드맵 `MCI-103`)에서만 고른다. E1 시점의 정적 블록이 그 모듈과 다른 형태면 승격 시 본문을 다시 써야 하므로 Experience Upgrade가 성립하지 않는다.

| candidateModule | E1 정적 블록의 필수 형태 |
| --- | --- |
| `quiz` | 선택지 제시 → 독자 선택 유도 문장 → 단락을 바꿔 정답과 해설 |
| `compare` | 두 대상을 같은 조건에서 나란히 → 차이가 드러나는 한 지점 → 판단 기준 |
| `reveal` | 관찰 대상 제시 → 독자가 먼저 떠올리게 함 → 항목별 공개 |
| `checklist` | 실행 직전에 확인할 항목 목록 → 미충족 시 행동 |

> 데이터 표(`#TABLE`)는 이 네 형태 중 어느 것도 아니다. 독자가 예측할 틈 없이 답을 한꺼번에 펼치므로 참여 지점이 0이다. 비교를 **요약**하는 보조 수단으로만 쓰고, 비교 자체는 위 `compare` 형태로 먼저 만든다.

- 슬롯은 E1에서도 예약할 수 있지만 빈 UI나 미구현 기능을 독자에게 노출하지 않는다.
- 각 슬롯은 JavaScript·외부 서비스 실패 시에도 핵심 답을 읽을 수 있는 `staticFallback`을 갖는다.
- 한 기사에는 Primary interaction 1개, Supporting interaction 1~2개까지만 둔다.
- 서비스 연결은 기사 품질을 높일 때만 사용한다. 카테고리만 보고 자동으로 Gen Studio를 붙이지 않는다.
- Magazine 기사에서 Play로의 직접 진입·Embed·복귀를 요구하지 않는다. Magazine Intelligence는 별도 Interactive Story의 선택적 source reference다(2026-10-09 PTU-Q-015). Tutors는 서비스를 종료했다.
- `entrySectionId`·`returnSectionId`는 실제로 승인된 Magazine 기사 경험·링크(예: Gen Studio 확장)에만 적용한다. Interactive Story·Play Story의 진입·복귀 계약과는 분리한다.
- 기사 안 AI 대화·이미지 생성 위젯(Article Embed)은 추진을 종료했다(2026-10-09 PTU-Q-016 D-3). 기사 내 interaction은 `staticFallback`을 갖는 정적 모듈에 한정한다.

## 26. 서비스 연결과 편집 신뢰 게이트

- **서비스 체험은 기사 끝의 CTA가 아니라 독자가 그 도움을 가장 필요로 하는 Episode 직후에 둔다.** 문제를 막 이해한 순간이 행동 확률이 가장 높고, 결론부의 서비스 CTA는 기사와 분리된 광고로 읽힌다. 위치는 `expansion.entrySectionId`로 선언한다.
- 기사의 마지막 행동은 서비스 사용이 아니라 관계 행동(저장·팔로우·다음 실험 따라가기)으로 닫아도 된다. 서비스는 결론이 아니라 문제 해결 과정 중간에 등장한다.
- Magazine은 연결 의도와 콘텐츠 맥락만 선언한다. 서비스 이용 가능 여부·인증·권한·과금·Pilot 허용 여부는 서비스 측이 fail-closed로 판정한다.
- 독립 서비스 링크와 인라인 연동의 공개 수준은 `SERVICE-ROLE-MAP.md`의 Product Maturity × Magazine Exposure 계약을 따른다.
- AI 생성 결과는 편차가 있으며 발행·상업적 사용 전에 검토해야 한다는 고지를 둔다. 학습 기능은 학습 결과를 보장하지 않는다.
- 금융·투자·세무·의료·법률 기사의 Interaction은 판단 교육과 정보 이해에 한정한다. 개인화된 추천·진단·매수/매도 지시처럼 오인될 모듈은 사용하지 않는다.
- 기사 자체의 답과 근거가 서비스 체험 없이도 완결되어야 한다. 서비스 사용을 정답 확인이나 핵심 정보 열람의 조건으로 만들지 않는다.

### Archetype별 Expansion 기본값 (신설 2026-08-28)

> 2026-10-09 개정 — `mystery`·`teardown`의 종전 기본값 `Tutors 질문`은 Tutors 서비스 종료로 폐기했다. Play CharacterChat CTA로 자동 변환하지 않는다(PTU-Q-015).

**기본값이지 강제가 아니다.** 기사 맥락이 다르면 벗어날 수 있고, 벗어난 이유를 `expansion`에 적는다.
어느 경우에도 기사당 Primary 서비스 1개 상한과 Primary CTA 1개 + 보조 1개 상한은 유지한다.

| Archetype | Primary 확장 | 보조 |
| --- | --- | --- |
| `mystery` | 없음 (관계 행동으로 닫음) | 저장 · 관련 글 |
| `teardown` | 없음 (관계 행동으로 닫음) | 저장 · 오류 지점 다시 보기 |
| `decision` | 없음 (관계 행동으로 닫음) | 저장 · 관련 사례 |
| `make` | Gen Studio 생성 | 체크리스트 저장 |
| `experiment` | 없음 (관계 행동으로 닫음) | 결과 비교 · 관련 글 |
| `simulator` | 입력값 바꿔보기 | 저장 · 관련 개념 |
| `build` | 없음 (관계 행동으로 닫음) | 이어 읽기 · 토픽 팔로우 |

- **관계 행동(저장·팔로우·이어 읽기·뉴스레터)은 아직 배포되지 않았다.** 배포 확인 전까지 CTA로 쓰지 않으며,
  이 표의 보조 항목도 배포된 것만 사용한다.
- `decision`·`experiment`·`build`에 Primary 서비스가 없는 것은 누락이 아니라 판정이다. 이 유형의 독자는
  결론 뒤에 도구를 찾지 않고 판단을 굳히려 한다.

## 27. AMU Reality Lens (편집 세계관, 신설 2026-08-27)

> **Magazine의 Canon은 Reality다.** Play의 세계관은 AMU가 정의하지만, Magazine의 세계관은 현실을 대체하지 않는다.
> Reality Lens는 허구 설정이 아니라 **현실을 시스템으로 해석하는 편집 관점**이다.

AMU Magazine은 투자·비즈니스·심리·AI·자기관리처럼 서로 멀어 보이는 주제를 함께 다룬다. Reality Lens는 이 다주제성을 약점이 아니라 "현실이라는 하나의 큰 시스템을 여러 각도에서 설명한다"는 일관된 정체성으로 바꾸기 위한 편집 계층이다.

### 27.1 권한 계층 — 무엇을 바꿀 수 있고 없는가

| 층 | 자유도 | 규칙 |
| --- | --- | --- |
| 사실 | 0% | 관측·수치·발표·인용은 변형 금지. Lens 때문에 현실을 바꿔 쓰지 않는다 |
| 해석 | 제한적 | AMU 관점의 인과·의미 부여 가능. 근거를 넘어선 단정은 금지 |
| 은유 | 자유 | 시스템·자원·힘의 비유로 이해를 돕는다. 단 은유가 실제 메커니즘과 어긋나면 폐기한다 |
| 시뮬레이션 | 자유 | 가정을 **명시**할 때만 허용. 가정 없는 예측을 사실처럼 쓰지 않는다 |

- **은유 정확성 검증은 필수다.** 비유가 독자에게 틀린 인과를 심으면 Lens가 아니라 오보다. 은유를 쓴 문단마다 "이 비유가 실제 원리와 어긋나지 않는가"를 확인한다.
- 사실층 규칙은 `PROOF-BANK.md`와 QA Gate의 미검증 표현 금지 조항을 그대로 따른다.

### 27.2 Category Lore — 카테고리별 세계

각 카테고리를 하나의 시스템으로 보고 `자원 / 행위자 / 힘`을 정의한다. 아래는 기본 매핑이며, 기사마다 전부 나열하지 않고 필요한 축만 쓴다.

| 카테고리 | World | 자원 | 힘(Forces) |
| --- | --- | --- | --- |
| Economy · Investment · Real Estate | Capital | 돈 · 신용 · 자산 | 금리 · 물가 · 유동성 · 위험 |
| Business & Strategy · Startup | Market | 자본 · 사람 · 주목 · 기술 | 수요 · 공급 · 유통 · 네트워크 효과 |
| Marketing Strategy · Growth & Analytics | Attention | 주목 · 신뢰 · 도달 | 관련성 · 빈도 · 확산 · 피로 |
| Self Management · Mindset · Success & Psychology | Player | 시간 · 에너지 · 지식 · 관계 | 습관 · 동기 · 회복 · 판단 |
| AI & LLM · AI Creatives | Tooling | 연산 · 데이터 · 모델 · 프롬프트 | 자동화 · 품질 편차 · 비용 곡선 |
| Stories · Services | Build | 결정 · 제약 · 시간 | 트레이드오프 · 되돌림 비용 |

### 27.3 노출 강도 — 기사 유형별로 다르게 쓴다

모든 글에 세계관을 같은 농도로 바르면 차별화가 아니라 **기믹**이 된다.

| 기사 유형 | Lens 비중 | 형태 |
| --- | --- | --- |
| 일반 검색 · Utility | 10~20% | 명확한 답 + 은유 1~2회, 본문 한 곳에 집약 |
| Authority · Mechanism | 20~40% | 시스템 모델로 원리 설명 |
| 인터랙티브 기사 · 특집 | 50~70% | 시나리오 · 선택 · 시뮬레이션 (기사 안의 편집 콘텐츠 유형 — 독립 Interactive Story Content System의 Story와 다르다) |

- **제목·`seoTitle`·slug·메타 설명에는 Lens 용어를 쓰지 않는다.** 검색 사용자가 무슨 글인지 알 수 없게 만들면 SEO와 신뢰를 모두 잃는다.
- 은유는 흩뿌리지 말고 **한 곳에 모은다.** 문단마다 조금씩 바르면 정보 밀도만 떨어진다.
- 금융·투자·세무·의료·법률 기사(Charter R4 고정)에서 Lens는 설명 보조로만 쓰고, 시뮬레이션에는 가정·한계를 반드시 표기한다. 개인화된 판단 지시로 읽힐 은유는 쓰지 않는다.

### 27.4 메타 필드 (선택)

Brief에 아래를 **선택 필드**로 남길 수 있다. §25 필수 메타에 추가되는 항목이 아니다.

```text
realityLens { world, intensity, anchorSectionId }
  world           Capital | Market | Attention | Player | Tooling | Build
  intensity       light | standard | heavy   (27.3의 세 구간)
  anchorSectionId 은유를 집약한 Episode
```

**적용 여부는 `content-ledger.jsonl`에 함께 기록한다.**

```json
"realityLens": {"world": "Capital", "intensity": "standard", "applied": true}
```

Brief 메타(`episodes`·`qualityEvidence`·`realityLens` 등)는 WordPress에 완전한 형태로 저장되지 않는다. 현재 발행 경로는 본문 필드와 Yoast 3키(`_yoast_wpseo_focuskw`·`_yoast_wpseo_metadesc`·`_yoast_wpseo_title`)를 보내고, 별도 등록 경로로 Article Experience 선언을 저장할 수 있다. Article Intelligence는 `INTELLIGENCE-PATTERN-POLICY.md`의 분리 계약과 `MCI-107` 이후의 별도 post meta를 따른다. Reality Lens 적용 여부는 여전히 ledger가 추적하므로 이 기록이 없으면 27.5의 승격 판정을 수행할 수 없다.

### 27.5 현재 상태와 금지

- **Reality Lens는 검증 단계다.** 품질 게이트·SEO 게이트·임베드 계약의 **하드 게이트가 아니며**, 누락을 이유로 기사를 `blocked` 처리하지 않는다.
- 프로토타입 근거: `.agent/references/AMU_GAME/amu_ooc_system_improvement.md`, 첫 적용 사례는 2026-08-27 Investment 리뉴얼 실험.
- 승격 조건: 적용 기사와 미적용 기사의 소비·재방문 지표 비교로 효과가 확인되면 그때 게이트로 올린다. 그 전까지 강제하지 않는다.
- 금지: `Universe` · `Player` · `Quest` · `Level` · `NPC` 같은 게임 용어를 독자에게 보이는 제목·소제목에 노출하는 것. 내부 메타 용어일 뿐이다.
- 금지: Lens를 근거 부족의 은폐 수단으로 쓰는 것. 은유는 근거를 대체하지 않는다.

## 28. Editorial Cover System (신설 2026-08-28)

커버(썸네일)는 기사를 요약하는 자리가 아니라 **그 글의 세계에 들어가고 싶게 만드는 표지**다.

### 28.1 역할 분리

각 표면이 담당하는 것을 섞지 않는다. 커버가 설명을 맡으면 본문 인포그래픽이 할 일을 빼앗는다.

| 표면 | 담당 |
| --- | --- |
| Cover / Thumbnail | 감정·분위기·호기심·브랜드 인상 |
| 제목 | 이 글이 무엇에 관한 것인지 명확히 전달 |
| Hero 문장 | 제목이 약속한 것을 한 줄로 좁힌 편집 카피 (`heroLine`) |
| Hero visual | 기사의 핵심 질문 또는 첫 번째 증거 |
| 본문 visual | 설명·비교·데이터·검증 |
| Interaction | 직접 선택·질문·실험 |

**정보는 제목이 담당하고 감각은 이미지가 담당한다.** 커버와 제목이 한 세트로 완성되는 방식을 기본으로 한다.

`heroLine`은 제목의 반복이 아니라 **이 글을 읽으면 무엇을 알게 되는지의 한 줄 약속**이다.
검색용 제목(`seoTitle`)은 키프레이즈로 시작해야 하는 제약이 있어 편집적으로 좁히기 어렵다.
`heroLine`이 그 자리를 대신한다. Voice 축의 평가 대상이다.

### 28.2 커버 문법 5종

기사 성격에 맞는 하나를 고르고 `coverArtDirection.grammar`에 기록한다.

| 문법 | 쓰는 곳 |
| --- | --- |
| `portrait` | 사람·제품·대상 하나를 강하게 보여준다. 인물·창작자·패션·기업 소재 |
| `still_life` | 사물 하나를 상징적으로 배치한다. 경제·투자·기술·생산성 같은 추상 주제 |
| `conceptual` | 핵심 아이디어를 비유적 장면으로 만든다. 원리·전환·역설 소재 |
| `documentary` | 실제 현장·제품·사람·환경을 담는다. Build in Public·기업 사례 |
| `graphic` | 데이터·기술 주제를 추상 조형으로 표현한다 |

### 28.3 Editorial과 Decorative의 경계

좋은 커버는 예쁘기만 한 것이 아니라 **기사의 핵심 긴장을 시각적으로 품고 있다.**
`coverArtDirection.tension`에 그 긴장을 한 줄로 적는다. 적을 수 없으면 그 이미지는 장식이다.

기준은 하나다 — **설명하지 않되, 암시한다.**

### 28.4 금지 사항

- Before/After 라벨, 화살표, 빨간 원, 번호 배지, 오류 지점 표시, 단계 도식 등의 설명형 커버 금지 
- 커버 안에 기사 제목·headline을 다시 넣는 것 금지. 카드에 이미 제목이 붙는다
- 비주얼 목적이 아닌 단순 설명 목적을 위한 모든 텍스트 블록 금지
- 네온 회로, 뇌 홀로그램, 로봇 손, `AI vs HUMAN` 대비, 보라·분홍 그라데이션 AI 콘텐츠 클리셰를 떠올리게 하는 추상적 표현 금지
- 기사의 긴장이 담기지 않은 단순 브랜드 광고 컷 처럼 보이는 이미지 금지
- 커버 하나로 답까지 다 보여주는 것 금지. "뭔가 다른데?"까지만 보여준다
- 키비주얼 이미지를 왼쪽이나 오른쪽으로 정렬하여 불필요한 빈 여백을 만드는 것 금지 

### 28.5 홈·목록 정합

여러 기사가 한 화면에 놓이는 홈과 목록에서 잡지처럼 보이려면 커버가 서로 조용해야 한다.
강한 피사체 · 충분한 여백 · 일관된 조명 감도 · 최소한의 그래픽 · 텍스트 없음을 유지한다.
정보 카드처럼 복잡해지면 홈 전체가 시끄러워진다.

## 29. 독자 노출 표면 (신설 2026-08-28)

### 29.1 내부 설계 언어를 화면에 쓰지 않는다

`Article Experience` · `Interaction Slot` · `Experience Level` · `E1/E2/E3` · `Episode` ·
`Archetype` · `Content Role`은 **AMU 내부에서 무엇을 붙일지 판단하기 위한 설계 언어**다.
독자에게는 아무 의미가 없고, 화면에 노출되는 순간 가치가 아니라 인지 비용이 추가된다.

- 이 용어들을 독자에게 보이는 라벨·eyebrow·제목·버튼 문구로 출력하지 않는다.
- 화면에 보여줄 것은 하나다 — **지금 여기서 무엇을 할 수 있는가.**
- 내부 메타·JSON·관리 화면에서는 그대로 쓴다. 제약은 독자 표면에만 적용한다.

> 2026-08-28 실측: 기사 하단 블록이 `Article Experience`를 eyebrow로 그대로 노출하고 있었다.
> 독자는 콘텐츠를 읽으러 왔는데 플랫폼의 정보 구조를 먼저 해석해야 하는 상태가 됐다.

### 29.2 `primaryQuestion`은 독자에게 그대로 보이는 문장이다

`primaryQuestion`은 내부 메타 필드처럼 생겼지만 **화면에 그대로 출력된다.**
따라서 연구 질문이 아니라 독자가 실제로 입 밖에 낼 법한 말로 쓴다.

- 한 문장에 조건절·병렬 명사구를 여러 개 쌓지 않는다.
- 정의·범위·예외를 한 문장에 다 넣지 않는다. 그건 본문이 할 일이다.
- 소리 내어 읽었을 때 사람이 묻는 말처럼 들려야 한다.

```text
금지  의류 상품 페이지의 모델 착용샷을 AI로 만들 때, 어디까지가 실제로 쓸 수 있는
      범위이고 어디부터가 반품과 규제로 되돌아오는가
사용  AI 착용샷, 실제 상품 페이지에 어디까지 써도 괜찮을까?
```

### 29.3 확장 경험의 위치

독자가 일반론을 다 읽고 **"그래서 내 경우는?"**이 생기는 지점에 둔다.

- 위치는 **결론이 끝난 뒤, 참고 자료가 시작되기 전**이다. 참고 자료 뒤는 늦다.
- 서비스 이름을 앞세우지 않는다. 독자의 질문이 주인공이고 서비스는 출처 표시 정도의 위계다.
- 캐릭터를 쓰더라도 작은 아바타 + 이름 + 한 줄 역할까지만이다. 크게 노출하면 전문 정보에서
  캐릭터 챗봇 홍보로 톤이 바뀐다.

### 29.4 확장 경험은 기사의 두 번째 레이어다

서비스 연결의 목적은 독자를 다른 서비스로 보내는 것이 아니라 `Magazine → 서비스 → Magazine Return`
루프를 닫는 것이다. 연결 자체는 재방문 장치가 아니다.

> 범위(2026-10-09) — 이 절은 Magazine 기사에서 승인된 서비스 확장(예: Gen Studio)에만 적용한다. Play·Interactive Story에는 적용하지 않으며, 그쪽은 Magazine과 직접적인 UI·진입·복귀 의존성을 두지 않는다(PTU-Q-015).

- 기사 `postId` · `sectionId` · 제목 · 참고 자료 맥락을 서비스로 넘긴다.
- 서비스 응답에서 원래 기사의 정확한 섹션으로 돌아오는 경로를 제공한다(`returnSectionId`).
- 서비스 쪽 대화·결과에도 어느 기사에서 시작했는지 원문 맥락을 남긴다.

이 조건을 갖추지 못하면 확장 경험이 아니라 이탈 링크다.
