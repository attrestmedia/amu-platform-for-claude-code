# 분할 구현 정책 (AMU WEB / WordPress)

## 목적

신규 기능을 거대한 단일 PHP/JS/CSS 파일에 누적하지 않고, 기존 동작과 WordPress 계약을 보존하면서 변경·검증 가능한 책임 단위로 구성한다.

## 신규 구현 필수 규칙

- 구현 전에 사용자 흐름, 렌더링, 입력/검증, 권한, 저장, 외부 API, 스타일 책임을 구분한다.
- 아래 중 하나라도 해당하면 처음부터 별도 책임 단위로 분할한다.
  - 서로 독립적인 화면/탭/form/modal이 2개 이상
  - 서로 다른 nonce/capability 또는 저장·외부 호출 생명주기가 2개 이상
  - PHP 렌더링과 도메인/저장 로직이 함께 증가
  - 한 파일이 400줄을 넘을 것으로 예상되거나 리뷰 시 한 화면에서 전체 흐름을 파악하기 어려움
- 테마 렌더링은 기존 `template-parts`/컴포넌트 패턴, 도메인 로직은 기존 helper/service/class 구조, hook 등록은 bootstrap/registration 경계에 배치한다.
- CSS/JS는 기능 단위 asset 경계를 우선하되 작은 스타일을 파일 수만 늘리기 위해 기계적으로 분리하지 않는다.
- 공통화는 두 번 이상 실제 재사용되거나 동일한 계약을 공유할 때만 수행한다.

## 기존 구현 리팩토링 기준

- 현재 요청과 직접 관련된 파일이 아래 조건을 만족하면 작업 범위 내에서 `safe-refactor`를 우선 검토한다.
  - 독립적인 변경 이유가 2개 이상
  - 600줄 초과이며 렌더링·저장·외부 호출이 혼재
  - 1,000줄 초과인 수동 작성 코드
  - 같은 블록/처리 흐름이 반복되어 한 수정이 여러 위치에 필요
- 600줄 초과 파일은 분할 계획과 보류 사유를 보고서에 기록한다.
- 1,000줄 초과 수동 작성 코드는 원칙적으로 분할한다. 생성 코드, vendor, migration/schema snapshot, 단순 데이터 원장은 예외이며 예외 사유를 기록한다.
- 요청 밖 정리로 범위를 넓히지 않는다. 필요한 리팩토링이 현재 승인 범위를 넘으면 적용 가능한 단계와 위험을 먼저 보고한다.

## 테마 마운트 쓰기 권한 임시 상향 (신규 파일 생성이 필요할 때)

WordPress 테마 디렉터리는 `www-data:www-data 755`, 파일은 `775`다. 에이전트 계정은 `www-data` 그룹에 속하므로
**기존 파일 수정은 되지만 신규 파일 생성은 되지 않는다.** 이 제약 때문에 분할해야 할 코드를 기존 파일에
인라인으로 눌러 담는 우회는 **금지한다.** 대신 아래 절차로 권한을 임시 상향하고 작업 후 반드시 원복한다.

### 적용 조건 (모두 충족할 때만)

- 대상이 **AMU Magazine WordPress 테마(`wordpress/wp-content/themes/**`)의 개선 작업**일 것
- 위의 "신규 구현 필수 규칙" 또는 "기존 구현 리팩토링 기준"에 따라 **파일 분리가 정당화**될 것
- 상향 범위가 **분리 대상 파일이 들어갈 디렉터리로 한정**될 것 (테마 루트 전체·재귀 상향 금지)

### 절차

권한 변경은 **테마를 bind mount로 물고 있는 WordPress 컨테이너(root)를 경유**한다. 호스트 `sudo`를 쓰지 않는다.

```bash
WP=amu_app-wordpress-1
T=/var/www/html/wp-content/themes/amu24

# ① 사전 기록 — 원복 기준값을 먼저 남긴다
docker exec $WP stat -c '%U:%G %a %n' $T/<대상디렉터리>

# ② 상향 (755 → 775). 대상 디렉터리만, -R 금지
docker exec $WP chmod g+w $T/<대상디렉터리>

# ③ 파일 생성·분리 작업 수행

# ④ 소유권·권한 정규화 — 신규 파일을 기존 파일과 같은 상태로 맞춘다
docker exec $WP sh -c "chown www-data:www-data $T/<신규파일> && chmod 775 $T/<신규파일>"

# ⑤ 원복 (775 → 755). 작업 성공·실패와 무관하게 반드시 수행
docker exec $WP chmod g-w $T/<대상디렉터리>
docker exec $WP stat -c '%U:%G %a %n' $T/<대상디렉터리>   # ①과 일치 확인
```

### 규칙

- **원복은 작업 단위 안에서 끝낸다.** 다음 작업이나 다음 세션으로 미루지 않는다. 검증에 실패해 롤백하더라도 ⑤는 수행한다.
- **⑤까지 마친 뒤 ①과 같은 값인지 재확인**하고, 그 결과를 보고서 검증 표에 적는다.
- `chmod -R`, 테마 루트 상향, `777`, 소유권 변경(디렉터리)은 금지한다.
- WordPress 컨테이너가 떠 있지 않으면 권한 상향을 시도하지 말고, 컨테이너 기동을 먼저 제안한다.
- 상향한 디렉터리 목록·원복 결과·신규 파일의 최종 소유권을 보고서에 남긴다.

## 안전한 분할 순서

1. 현재 공개 함수, hook, shortcode, REST/AJAX 계약과 렌더 결과를 고정한다.
2. 순수 helper 또는 leaf template/UI부터 한 단계씩 추출한다.
3. 권한·입력 검증·저장·외부 호출 순서를 변경하지 않는다.
4. 각 단계마다 `php -l`, 관련 테스트/테마 빌드, 필요 시 시각 검증을 수행한다.
5. 최소 diff와 파일별 책임, 롤백 방법을 보고한다.

## 금지 사항

- 줄 수를 맞추기 위한 의미 없는 wrapper/파일 생성
- WordPress hook 이름, priority, nonce/capability, 응답 포맷을 분할 과정에서 함께 변경
- 분할과 기능 추가, 디자인 전면 변경, 의존성 교체를 하나의 단계에 혼합
- 모든 기능 상태/함수를 하나의 전역 singleton 또는 범용 helper에 다시 집중
- **디렉터리 쓰기 권한이 없다는 이유로 분리 대상 코드를 기존 파일에 인라인으로 누적** — 위 "테마 마운트 쓰기 권한 임시 상향" 절차를 따를 것
- **상향한 권한을 원복하지 않은 채 작업 종료**
