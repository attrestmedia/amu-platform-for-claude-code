# WordPress Theme UI (AMU24)

## 기본 원칙

- 모바일 퍼스트 우선 (레이아웃 · 간격 · 터치 타겟)
- 기존 테마 구조 · 헬퍼 · 토큰을 먼저 찾고 재사용한다. 무단 구조 변경 금지
- CSS/JS 변경은 영향 범위(레이아웃 · 성능 · SEO · 접근성)를 3~6줄로 요약한 뒤 최소 수정
- 반복되는 스타일 조합은 **실제 반복이 확인된 뒤에만** 공통화한다. 과잉 추상화 금지
- 아이콘은 lucide 우선. 단독 svg 난립 금지
- 예쁜 화면이 아니라 **사용자의 다음 행동을 만드는 화면**을 우선한다

## 스타일 소스 정본 — SCSS만 수정한다

**`assets/css/*.css`는 빌드 산출물이다. 절대 직접 수정하지 않는다.**
스타일 추가·수정·삭제는 항상 `assets/css/scss/` 아래 SCSS에서 하고, 컴파일해서 반영한다.

```text
정본   assets/css/scss/**.scss
산출   assets/css/*.css  +  *.css.map        ← 직접 편집 금지
```

- 컴파일된 `.css`에 규칙을 덧붙이면 **다음 빌드에서 통째로 사라진다.**
  실제로 그렇게 추가된 뉴스레터·계정 UI 스타일이 SCSS에 없는 채로 운영에 남아 있었고,
  2026-09-01에 SCSS로 역반영했다.
- `.css`만 고치고 SCSS를 갱신하지 않는 우회는 권한 문제·빌드 도구 부재를 이유로도 허용하지 않는다.
  빌드가 막히면 그 사실을 보고하고 중단한다.
- 새 파티션이 필요한데 `scss/` 디렉터리 쓰기 권한이 없으면
  `split-implementation.md`의 임시 상향 절차를 따르고 같은 작업 단위에서 원복한다.
  권한이 없다는 이유로 산출물에 인라인으로 누적하지 않는다.

### 빌드 명령

테마에 빌드 스크립트가 없으므로 `sass` CLI를 직접 쓴다. 엔트리는 `scss/<name>.scss` → `<name>.css` 1:1이다.

```bash
cd amu_app/wordpress/wp-content/themes/amu24/assets/css
sass --style=compressed scss/<name>.scss <name>.css
# 산출물 선두의 BOM은 제거한다 (기존 파일 형식과 맞춘다)
```

- 산출물 형식 계약: **BOM 없음 + compressed + 끝에 `sourceMappingURL` 주석 + 후행 개행 1**
- 변경 전 상태에서 재컴파일했을 때 기존 파일과 **byte 단위로 같아야** 한다.
  다르면 소스와 산출물이 어긋나 있다는 뜻이므로 먼저 원인을 확인한다.
- 수정한 엔트리만 다시 빌드하고, 무관한 산출물을 함께 커밋하지 않는다.

### 변경 후 확인

1. 재컴파일 diff가 **의도한 구간만** 바뀌었는지 확인한다
2. 규칙 수·셀렉터가 소실되지 않았는지 확인한다 (형식 차이는 무시, 규칙 소실은 실패)
3. 서빙되는 CSS의 HTTP 200과 크기를 확인한다

## 색상 모드 지원 범위

- **현재 amu24는 light-only다.** `base/_colors.scss`의 dark 토큰 블록과 theme-toggle 스크립트가 모두 주석 상태다.
- dark 지원을 전제한 구현을 하지 않고, 검증에서도 dark 통과를 주장하지 않는다.
- 새 스타일은 색상 리터럴 대신 토큰(`var(--*)`)을 써서 dark 복구 시 토큰 교체만으로 대응할 수 있게 한다.
- dark를 되살릴 때 함께 손대야 하는 곳: `base/_colors.scss`의 주석 블록,
  `inc/actions/enqueue-scripts.php`의 theme-toggle enqueue, `header.php`의 토글 버튼.

## 화면 구성

- 화면마다 초점은 하나다. "이 화면의 주인공이 무엇인가"에 한 가지로 답할 수 있어야 한다.
- 섹션당 하나의 목적, 하나의 헤드라인, 하나의 짧은 보조 문장.
- 요소를 늘리기 전에 **그 요소가 사용자의 다음 행동과 연결되는지** 확인한다. 장식 목적의 반복 요소를 쌓지 않는다.
- 내비게이션 바를 가려도 AMU 브랜드로 식별 가능해야 한다 (브랜드 테스트).
- 서비스 소개·랜딩 성격의 페이지는 `정체성 → 맥락 → 설명 → 신뢰 → 전환` 흐름을 참고한다.
  **편집면(매거진 홈 · 아카이브 · 기사)에는 이 흐름을 적용하지 않는다.** 편집면의 첫 목적은 설득이 아니라 발견과 읽기다.

## 컨테이너 · 카드

- 카드 · 보더 · 섀도 · 배경은 **의미가 있을 때 쓴다.** 목록 항목의 경계, 상호작용 단위,
  밀도가 다른 콘텐츠의 구분이 그 예다.
- 같은 의미를 전달하는 컨테이너를 중첩하지 않는다 (카드 안의 카드 안의 박스).
- 카드 사용 여부를 전역 금지·허용으로 정하지 않는다. **해당 화면의 정보 구조가 정한다.**

## 이미지 · 오버레이

- 원본 비율을 존중하고 기본 crop을 하지 않는다. crop은 편집자가 focal point를 지정한 경우에만 한다.
- 이미지 위에 텍스트 · 라벨 · 배지를 올릴 때는 **대비를 확보한다**
  (하단 그라데이션, 반투명 레이어, 또는 이미지 밖 배치 중 택1).
- 이미지 위 정보가 잘리거나 가려지지 않는지 375px에서 확인한다.
- 메인 비주얼은 제품 · 장소 · 분위기 등 구체적 맥락을 보여준다. 장식적 추상 배경을 주인공 이미지로 쓰지 않는다.

## 금지

- **AI 슬롭 스타일** — 예측 가능한 나열형 레이아웃, 목적 없는 보라·분홍 그라데이션, 근거 없는 통계 배지
- 새 폰트 · 아이콘/UI 라이브러리 · 전역 색상 토큰 도입 (별도 승인 필요)
- 시스템 기본 폰트(Inter · Roboto · Arial) 하드코딩
- 색상 리터럴 하드코딩 — 토큰을 쓴다
- hover에서만 접근 가능한 기능
- 고정 · 플로팅 UI가 텍스트 · 버튼 · 핵심 콘텐츠를 가리는 배치

## 모션

- 의미가 있을 때만 사용하고 150~300ms 수준을 기본으로 한다.
- CSS transition/animation 우선. 필요할 때만 라이브러리를 검토한다.
- `prefers-reduced-motion`에서 이동 · burst 효과를 제거하되 상태 변화 자체는 유지한다.

## 검증

- 375 / 768 / 1024 / 1440px 가로 overflow 0
- 인터랙티브 요소 44x44px 이상, visible focus, 키보드로 도달 가능
- 이미지 `width`/`height` · `srcset` · lazy loading으로 CLS 통제
- `visual-check` 스킬로 캡처한 뒤 위 항목을 대조한다
