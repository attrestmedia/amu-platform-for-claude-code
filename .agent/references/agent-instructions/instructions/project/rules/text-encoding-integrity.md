# Text Encoding Integrity (한글 등 비ASCII 텍스트 전달 규칙)

## 목적

원본 텍스트에는 문제가 없는데 **에이전트가 옮겨 적는 단계에서** 한글이 깨져 저장되는 사고를 막는다.
이 사고는 조용히 발생한다 — 이스케이프 한 글자가 틀려도 결과가 "유효한 다른 음절"이 되므로 오류로 보이지 않고 그대로 저장된다.

> 실제 사례: gen-studio 템플릿 태그를 `숬`로 잘못 써서 `오버 더 숄더`가 **`오버 더 숬더`**로 운영 DB에 저장됨.
> 원본 문자열은 정상이었고, 깨진 것은 전달 표현뿐이었다.

## 1. 기본 원칙 — 리터럴 전달

- 한글·일본어·중국어·이모지 등 **비ASCII 텍스트는 항상 리터럴 UTF-8로 전달**한다.
- **손으로 작성한 이스케이프는 모든 형식에서 금지**한다.
  - 금지: `가` 형태 유니코드 이스케이프, `\xEA\xB0\x80` 바이트 이스케이프
  - 금지: `&#xAC00;` / `&#44032;` HTML 엔티티로 한글 표현
  - 금지: `%EA%B0%80` percent-encoding으로 한글 표현 (URL 경로 자체가 인코딩을 요구하는 경우는 예외)
- 도구가 JSON 문자열을 받더라도 **리터럴 한글이 정상 입력**이다. 이스케이프해야 안전하다는 판단은 틀렸다.

## 2. 적용 범위

아래 **모든** 쓰기 경로에 적용한다. 특정 MCP나 특정 도구에 한정되지 않는다.

| 경로 | 예 |
| --- | --- |
| MCP 도구 인자 | `genstudio` 템플릿 `title`/`tags`/`templateText`, `marketing-ops` 콘텐츠 draft, `amu-magazine` 기사 |
| Agent API 페이로드 | `/api/ai/agent/*` 요청 본문 |
| 파일 쓰기 | 보고서 `.md`, 기사 원고, 정책 문서 |
| JSON 원장·로그 | `.agent/logs/**/*.json`, `todo-content.json`, `content-ledger.jsonl` |
| 코드/설정 | 소스의 한글 문자열, i18n `{ko: "..."}` |
| 커밋 메시지·PR 본문 | — |

## 3. 근본 원인 통제 — 손으로 전사하지 말 것

이 사고의 실제 원인은 이스케이프 자체보다 **긴 텍스트를 손으로 다시 옮겨 적는 행위**다.

- 수십 줄 이상이거나 반복 구조인 페이로드는 **파일에 먼저 만들고 스크립트로 직렬화**해 전달한다. 눈으로 옮겨 적지 않는다.
- Python으로 JSON을 쓸 때는 `json.dump(..., ensure_ascii=False)`를 사용한다. 기본값(`True`)은 한글을 전부 `\uXXXX`로 바꾼다.
- Node/JS의 `JSON.stringify`는 기본적으로 리터럴을 유지하므로 별도 옵션이 필요 없다.
- 셸에서는 `echo` 대신 heredoc 또는 파일 입력을 사용하고, 셸이 백슬래시를 재해석하지 않는지 확인한다.

## 4. 필수 검증 — 쓰고 나서 되읽는다

한글이 포함된 쓰기 작업은 **저장 후 재조회해 원문과 대조**한다. 응답 echo만 훑고 넘기지 않는다.

- 우선 확인 대상: 고유명사, 외래어 표기(숄더/셔터/브릿지), 복합 명사, 조사가 붙은 어절
- MCP: 등록 응답 본문 + 필요 시 재조회 도구(`get_prompt_template`, `read_post`, `get_job`)로 확인
- 파일: 저장 후 해당 구간을 다시 읽어 확인
- 자동 점검이 가능하면 우선한다 — 예: 원본과 저장본의 문자열 diff, 완성형 밖 음절 탐지

## 5. 깨짐을 발견했을 때

1. **즉시 정정**한다. 다음 작업으로 넘어가기 전에 처리한다.
2. 정정 수단은 도구별 안전 절차를 따른다.
   - gen-studio 템플릿: `strictNew=false`로 재등록 (key 변경 금지)
   - WordPress: 기존 slug 유지한 채 본문/메타만 갱신
3. 같은 작업에서 저장한 **다른 필드도 함께 검수**한다. 전사 오류는 단독으로 발생하지 않는 경향이 있다.
4. 보고서·로그에 발생 사실과 정정 결과를 남긴다. 조용히 고치고 넘어가지 않는다.

## 6. 예외

- 프로그램이 생성한 직렬화 결과에 이스케이프가 포함되는 것은 문제가 아니다. **사람(에이전트)이 손으로 쓰는 경우만 금지**한다.
- 규격상 ASCII만 허용되는 필드(일부 config key, 파일명 제약 등)는 이스케이프 대신 **로마자 표기나 영문 slug**를 쓴다. 한글을 이스케이프로 우겨넣지 않는다.
- 이스케이프가 불가피하면 스크립트로 생성하고, 그 사실과 검증 방법을 보고서에 남긴다.
