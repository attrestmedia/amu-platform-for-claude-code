# Cross-Project Rules

## 목적
두 개 이상의 프로젝트를 동시에 변경하는 교차 작업에서 계약 불일치, 파편화된 검증, 롤백 누락을 방지한다.

## 교차 작업 판별

- Node API 응답 포맷 변경 + Native WebView 호출 로직 변경 → 교차
- WordPress REST 연동 변경 + Node API 변경 → 교차
- 단일 프로젝트 내부 완결 작업 → 교차 아님

## 교차 작업 절차

1. **계약 확정 우선**: API/응답 포맷/에러 포맷/인터페이스 스키마를 먼저 확정하고, 양쪽이 동의할 수 있는 형태로 제시
2. **변경 순서 명시**: 어느 프로젝트를 먼저 수정하고 어느 쪽을 후속 반영하는지 순서를 선언
3. **프로젝트별 검증 분리**: 각 프로젝트의 검증 도구를 독립적으로 실행
   - Node: `pnpm` 기반 scripts
   - Native: `flutter analyze`, `flutter test`
   - WP/Infra: `php -l`, `docker compose config`
4. **통합 보고**: 변경 파일 목록 / 위험 요소 / 후속 작업을 하나의 보고서로 통합 정리

## 제약

- 한쪽 프로젝트의 변경이 다른 쪽의 기존 계약을 깨뜨리는 경우, 반드시 영향 범위를 사전 요약
- 교차 작업에서 범위 밖 리팩토링은 절대 금지 — 계약 변경분만 최소 수정
- **각 프로젝트는 별개의 git 저장소다.** `amu_app`과 `amu_app/node-app`처럼 경로가 이어져 있어도
  저장소가 다르면 커밋도 저장소별로 따로 만든다. "두 프로젝트를 함께 커밋"은 두 개의 커밋을 뜻한다 —
  저장소 목록과 경계는 `{{AGENT_ROOT}}/rules/repository-topology.md` 정본을 따른다
