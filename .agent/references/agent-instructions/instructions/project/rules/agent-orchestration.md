# Agent Orchestration — Main + Subagents 실행 규칙

## 목적

여러 단계·여러 스코프에 걸친 작업을 **Main 에이전트 1인이 조사부터 구현·자기검증까지 전부 수행**하는 방식은
확증편향과 컨텍스트 포화를 만든다. 이 룰은 Main을 오케스트레이터로 두고 실제 작업을
난이도가 아니라 **위험도 기준**으로 서브에이전트에 위임하는 공통 절차를 고정한다.

정책 내용은 여기서 정의하지 않는다. 이 룰은 **누가·어떤 순서로 실행하는가**만 규정하며,
무엇을 해도 되는지는 기존 룰과 `.agent/amu-platform-guide/`가 정한다. 어긋나면 그쪽이 우선한다.

## 1. 적용 대상

| 적용한다 | 적용하지 않는다 |
| --- | --- |
| `.agent/todo-*.json` 원장 실행 | 단일 typo·import·이름 변경 |
| 3개 이상 파일을 바꾸는 구현 | 명확한 설정값 1개 변경 |
| 교차 스코프 작업(`{{AGENT_ROOT}}/rules/cross-project.md`) | 읽기 3회 이하로 끝나는 사실 확인 |
| 규제·법무·인증·경제 게이트가 걸린 작업 | 단일 명령 실행과 결과 보고 |
| 원인이 불명확한 장애 분석 | 이미 확정된 1파일 패치 |

**서브에이전트를 만드는 것 자체가 목표가 아니다.** 한 에이전트로 명확하고 안전하게 끝나면 그렇게 한다.
위임 비용(컨텍스트 전달·결과 통합·충돌 검토)이 이득보다 크면 Main이 직접 처리한다.

## 1.1 대량 일괄 변경 금지 (Bulk Edit Prohibition)

**수십~수백 개 파일을 한 번의 스크립트·정규식 치환·find/replace로 일괄 변경하는 작업은 원칙적으로 금지한다.**

대량 변경은 파일 수에 비례해 (1) 치환 누락·오치환, (2) 중간 실패 시 일부만 반영돼 전체가 비일관,
(3) 되돌리기 어려운 비가역 손상 위험이 급증한다. 이는 복구가 불가능한 사고로 이어진다.
(사고 사례: 2026-09-05 버튼 variant 일괄 치환 스크립트가 40개 파일을 파손해 복구 불가 상태가 됨)

대량 변경이 불가피한 경우 **반드시 절차별로 세분화된 단위 작업**으로 쪼개서 진행한다:

1. **세분화** — 전체를 한 번에 바꾸지 말고, 독립적으로 변경·검증 가능한 단위로 나눈다.
   (예: 계약/타입 변경 → 소비부 치환 → 패키지 재배포 → 최종 검증, 순으로 나눠 단계별 진행)
2. **단계별 검증** — 각 세분 단계를 마칠 때마다 lint/typecheck/test를 돌려 중간 실패를 즉시 포착한다.
3. **사전 백업** — 작업 전 워킹트리 전체 diff/백업을 남겨 언제든 되돌릴 수 있게 한다.
4. **가역 단위 유지** — 한 단계가 안전하게 되돌릴 수 있는 크기를 넘지 않게 한다. 되돌릴 수 없게 커지면 즉시 중단하고 사용자에게 보고한다.
5. **자동 치환 dry-run** — 파서·정규식 일괄 치환은 전체 적용 전 표본에 dry-run하고, 적용 후 원문과 대조한다. 미검증 상태로 전체 실행하지 않는다.

**이름만 바꾸는 의미 보존 변경은 §1.2 의 통제된 예외를 따른다.** 이 절의 금지는 동작을 바꾸는 일괄 변경에 그대로 적용된다.

## 1.2 통제된 일괄 이름 변경 (Controlled Bulk Rename) — 2026-09-21 신설

**§1.1 의 금지는 기본값이지 영구 동결이 아니다.** 알려진 잘못된 이름·경로를 "일괄 변경이 금지라서"
그대로 두면 그 자체가 장기 리스크가 된다. 회피 수단(alias 재export 등)은 이름을 둘로 늘려
새 코드가 어느 쪽을 써야 하는지 판단을 매번 반복하게 만든다.
근거: 2026-09-21 사용자 판정 — "장기적으로 틀린 이름인데 규칙 때문에 개선을 하지 못한다면
이는 결국 장기적인 리스크 요인을 남겨두는 것과 같다."

아래 **다섯 조건을 전부** 만족할 때 일괄 변경을 허용한다. 하나라도 빠지면 §1.1 의 금지가 그대로 적용된다.

1. **승인** — 사용자 승인 또는 원장 게이트 승인이 있다. 에이전트가 스스로 착수하지 않는다.
2. **의미 보존에 한한다** — 식별자·타입명·경로·컬렉션명처럼 **동작을 바꾸지 않는 이름 치환**만 대상이다.
   로직·분기·기본값·권한 판정을 함께 바꾸는 변경은 여전히 금지하며, 이름 변경과 **반드시 분리한다.**
3. **alias 경유 단계적 이행을 기본형으로 한다** — 아래 4단계이며, **모든 단계가 각각 컴파일되고
   각각 되돌릴 수 있어야 한다.** 중간에 중단해도 구 이름이 살아 있어 부분 반영 상태가 동작한다.

   ```text
   1단계  신규 이름 정본 추가 + 구 이름을 신규 이름의 alias 로 유지   (동작 불변, typecheck 통과)
   2단계  소비부를 디렉터리·레이어 단위로 나눠 치환                   (단계마다 typecheck·lint 통과)
   3단계  alias 제거                                                (여기서 처음으로 구 이름이 사라진다)
   4단계  잔존 grep 0건 확인 + 전체 typecheck·lint·test             (리더가 통합 단계에서 판정)
   ```

4. **타입 인지 도구를 우선한다** — `ts-morph`·컴파일러 기반 rename symbol 을 쓴다. 정규식·문자열
   치환은 타입 인지 도구로 처리할 수 없는 문자열 리터럴(라우트 경로·컬렉션명·권한 키)에만 쓰고,
   그 경우 **대상 목록을 먼저 파일:라인으로 열거한 뒤** 치환하고 적용 후 원문과 대조한다.
5. **사전 백업과 단계별 검증** — 착수 전 워킹트리를 커밋하거나 diff 를 아카이브한다. 각 단계 종료 시
   lint·typecheck 를 돌리고, 실패하면 그 단계에서 멈춘다. §1.1 의 3·4·5번은 그대로 유지된다.

**타입 검사는 식별자 치환에만 완전한 검증기다** (2026-09-21 ASH-07 실측으로 추가).
`tsc` 는 이름이 잘못 바뀌거나 빠지면 전부 타입 오류로 잡아 준다. 그래서 식별자 치환은 단계마다
typecheck 만으로도 안전하다. **문자열 리터럴은 다르다** — 라우트 경로·컬렉션명·권한 키·테스트 fixture
경로는 런타임에 해석되므로 타입 검사가 한 건도 잡지 못한다. 실측 사고: 라우트 디렉터리를 옮긴 단계에서
typecheck·lint 가 전부 통과했으나 계약 테스트가 하드코딩한 fixture 경로 2줄이 따라가지 않아
통합 단계에서야 `ENOENT` 로 드러났다.

따라서 일괄 이름 변경은 **두 종류를 나눠 검증한다.**

| 대상 | 검증 수단 |
| --- | --- |
| 식별자·타입명·함수명 | `typecheck` (완전) |
| 문자열 리터럴 — 라우트 경로·컬렉션명·권한 키·fixture 경로·쿼리 키 | **열거 → 치환 → 원문 대조 + 그 경로를 실제로 읽는 테스트 실행** |

**문자열 리터럴 치환 단계의 종료 조건에 `typecheck`·`lint` 를 쓰지 않는다.** 그 경로를 소비하는
테스트·런타임 검증을 실행해야 끝난 것이다. 계획서에 "typecheck 가 완전한 검증기다" 라고 적으려면
**식별자에 한한다는 단서를 함께 적는다** — 단서 없는 그 문장이 위 사고의 직접 원인이었다.

**데이터 저장소 이름(컬렉션·인덱스·권한 키)이 포함되면 코드 치환과 별개의 마이그레이션이다.**
dry-run 으로 대상 건수를 먼저 산출하고, 적용 순서와 롤백 경로를 코드 변경과 분리해 설계한다.
운영 데이터가 대상이면 `{{AGENT_ROOT}}/rules/safety-governance.md` 의 승인 경계를 함께 따른다.

**병렬 실행 조건** — 단계 2 의 소비부 치환은 write set 이 디렉터리 단위로 겹치지 않으면 병렬화할 수 있다.
단계 1 이 끝나 신규 이름 정본이 확정된 뒤에만 시작하며, 단계 3 은 병렬화하지 않는다(§6 병렬 BUILD 허용 조건).

## 2. 실행 티어 (모델명 대신 티어로 고정)

모델명은 바뀐다. 라우팅 판단은 **티어**로 기록하고, 티어→모델 매핑만 하니스별로 유지한다.

| 티어 | 성격 | Claude Code | Codex |
| --- | --- | --- | --- |
| **SCAN** | 탐색·검색·호출경로 추적·로그 조회·lint/typecheck 실행·체크리스트 대조 | Haiku | Luna(high) |
| **BUILD** | 설계가 확정된 구현·리팩터링·테스트 작성·UI 구현·스키마 반영 | Sonnet | Luna(xhigh) 또는 Terra(high or xhigh) |
| **JUDGE** | 설계 판단·원인 분석·보안/인증·데이터 정합성·비가역 변경 결정·독립 리뷰 | Opus | Sol(high or xhigh) |
| **FRONTIER** | JUDGE로도 결론이 서지 않는 최고난도 판단, 장기 horizon 복합 작업 | Fable | Sol(max) |

| **BUILD 적용 모델 판단 기준**         | Codex                |
| ---------------- | -------------------- |
| 반복적·기계적·결과 검증 쉬움 | **Luna xHigh**       |
| 일반적인 다중 파일 구현    | **Terra High**       |
| 복잡한 구현·부작용 추론 필요 | **Terra xHigh**      |
| 설계 자체가 불확실해짐     | **BUILD 중단 → JUDGE** |

- **Main 오케스트레이터는 JUDGE 티어를 유지한다.** 
  Main은 원장 전체 맥락·게이트 판정·최종 통합은 위임하지 않으며, 판단 권한을 유지하고 SCAN·BUILD 실행은 적절한 서브에이전트에 위임한다.
- FRONTIER는 **에스컬레이션 결과로만** 진입한다. 처음부터 FRONTIER로 시작하지 않는다.
- effort는 모델과 별개 축이다. 하니스가 지원하면 `티어 × effort` 2차원으로 지정한다. 
  (Claude Code는 호출 시점 `model` override가 가능하고 effort는 에이전트 정의 frontmatter에 둔다.)
- 모델 라우팅을 막는 전역 강제값을 두지 않는다.
  Claude Code: `CLAUDE_CODE_SUBAGENT_MODEL`을 구체 모델로 전역 고정하지 않는다.
  Codex: `agents.default_subagent_model`은 기본값으로 둘 수 있으나, explicit spawn model override를 허용한다.
- effort 라우팅을 막는 전역 강제값을 두지 않는다.
  Claude Code: `CLAUDE_CODE_EFFORT_LEVEL`이 subagent frontmatter effort보다 우선하므로 티어별 effort를 쓸 때 주의한다.
  Codex: `agents.default_subagent_reasoning_effort`는 기본값으로 둘 수 있으나, explicit spawn effort override를 허용한다.

## 3. 티어 판정 — 축의 최댓값으로 정한다

아래 9개 축을 평가하고 **가장 높은 축 하나가 티어를 결정한다. 평균을 내지 않는다.**

`Complexity` · `Ambiguity` · `Impact` · `Recovery Cost` · `Security` · `Data Risk` · `Compliance` · `Scope`

코드 난이도는 8개 중 하나일 뿐이다. **코드가 단순해도 되돌릴 수 없으면 JUDGE다.**

```text
wp_options에서 Gmail OAuth 토큰 삭제
  Complexity 낮음 · Impact 매우 높음 · Recovery Cost 높음 · Security 높음
  → JUDGE가 삭제 범위와 폴백 존재를 판정 → BUILD가 실행 → SCAN이 결과 확인
```

AMU에서 **무조건 JUDGE 이상**인 축:

- 인증·권한·자격증명 (`{{AGENT_ROOT}}/rules/safety-governance.md`)
- 코인 변동·비용 발생·보상 지급 (`amu_app/node-app/{{AGENT_ROOT}}/rules/server-economy-security.md`)
- 개인정보·법무·규제 게이트 (`{{AGENT_ROOT}}/rules/compliance-guardrails.md`)
- 데이터 마이그레이션·삭제·운영 DB 쓰기
- 배포·발행·발송처럼 외부에 나가는 비가역 동작
- 두 개 이상 스코프의 계약 변경 (`{{AGENT_ROOT}}/rules/cross-project.md`)
- Execution/Reasoning: `Complexity`, `Ambiguity`, `Scope`, `Repetition`(모델, effort, task 분해, 병렬화 결정 시)
- `Impact`, `Recovery Cost`, `Security`, `Data Risk`, `Compliance` 중 하나가 높은 경우

## 4. Main이 위임하지 않는 것 (하드 경계)

서브에이전트가 병렬로 돌면 **단일 파일에 대한 동시 쓰기**와 **게이트 우회**가 실제로 발생한다. 아래는 Main 전용이다.

| Main 전용 | 이유 |
| --- | --- |
| `.agent/todo-*.json` 원장 갱신 | 여러 서브에이전트가 같은 JSON을 쓰면 유실된다 |
| `.agent/logs/**/*.json` 기록 | 하루 1파일 구조라 동시 쓰기가 곧 손상이다 |
| `.agent/docs/project/**` 보고서 작성 | 통합 판단의 산출물이다. 조각을 이어붙이지 않는다 |
| `.agent/content/content-ledger.jsonl` append | append-only 원장의 순서·중복 판정은 단일 지점에서만 |
| 발행 cap(`uploadPolicy`) 판정 | fail-closed 규칙이다. 조회는 위임 가능, **판정은 위임 불가** |
| 규제·법무·SEO·production publish 게이트 판정 | 게이트는 통과 여부를 판단하는 주체가 하나여야 한다 |
| 외부 상태를 바꾸는 MCP 호출 | 카탈로그 표의 `방향`이 `W`·`C`인 도구. 조회(`R`) 계열만 위임한다 — 판정 기준과 예외는 `amu-custom-mcp` 스킬 §5.1 |
| `owner=user` 작업과 사용자 승인이 필요한 실행 | 배포·발송·DNS·콘솔 조작·결제·운영 데이터 삭제 |
| 최종 완료 판정 (`done` 처리) | 검증 충족 여부는 Main이 판단한다 |

서브에이전트는 이 항목들에 대해 **초안·조사·dry-run·명령어 준비·diff 준비까지만** 수행하고 결과를 반환한다.

## 5. 위임 계약 (서브에이전트 프롬프트 필수 항목)

서브에이전트는 이 세션의 맥락을 자동으로 갖지 않는다. 위임 프롬프트에 아래를 **명시적으로 적는다.**

1. **스코프** — 대상 워크스페이스 경로와 먼저 읽을 `{{AGENT_ROOT}}/overview/`·룰 경로
2. **역할과 티어** — explorer / architect / implementer / reviewer / verifier 중 하나 + 티어
3. **입력** — 파일 경로, 원장 TASK id, 선행 결과의 위치 (내용을 프롬프트에 옮겨 적지 말고 **경로로 넘긴다**. 단 **통제 정보는 직접 전달**)
4. **쓰기 권한** — 읽기 전용인지, 쓸 수 있다면 **허용 파일 경로 목록**을 열거
5. **금지** — §4 Main 전용 항목, 범위 밖 리팩터링, 승인 필요 작업 실행
6. **산출 형식** — 무엇을 어떤 형태로 반환할지 (근거는 `파일:라인`으로 인용, 미확인은 "추정"으로 표기)
7. **stop condition** — 설계 변경이 필요해지면 구현하지 말고 중단 후 Main에 반환

**한글 본문·기사 원고·프롬프트 템플릿을 서브에이전트 프롬프트에 복사해 전달하지 않는다.**
전사 단계가 늘어날수록 한글 훼손 사고가 늘어난다. 항상 파일 경로로 주고받는다 —
상세: `{{AGENT_ROOT}}/rules/text-encoding-integrity.md`

역할은 필요한 만큼만 만든다. 역할 이름을 늘리는 것이 분업이 아니다.

## 6. 병렬 / 직렬

**병렬화한다** — 서로 독립적인 read-only 작업

```text
Main
 ├─ SCAN: 관련 코드·호출 경로 조사
 ├─ SCAN: 기존 테스트·설정 현황
 ├─ JUDGE: 보안·규제 영향 분석
 └─ SCAN: 외부 문서·API 사양 확인
```

**직렬화한다** — 같은 대상을 쓰는 작업

- 같은 파일 / 같은 DB 스키마 / 같은 마이그레이션
- 같은 원장·로그·ledger (§4에 따라 애초에 Main 전용)
- 같은 WordPress 포스트, 같은 MCP 설정(`uploadPolicy`·keyword profile)
- 앞 단계 결과가 다음 단계 입력인 작업
- 교차 스코프 구현 — **계약 확정 전에는 병렬 착수 금지**, 확정 후 스코프별 분리는 허용

동시에 같은 파일을 고치는 서브에이전트를 두 개 이상 띄우지 않는다. 
**병렬 BUILD**는 **write set이 겹치지 않고, shared contract가 이미 확정되었으며, generated artifact/lockfile을 공유하지 않을 때**만 허용한다.

### 병렬 BUILD 허용 조건

1. write set 비중첩
2. shared contract 확정
3. generated artifact/lockfile 비공유
4. 동일 external state 비수정
5. 한 작업의 결과가 다른 작업의 입력이 아님

## 7. 기본 실행 순서

```text
원장·현재 상태 확인 (Main/JUDGE)
  → 실행 가능 task 선정 · step 분해 · step별 티어 판정
  → 조사 병렬 실행 (SCAN)
  → Main이 결과 통합 · 충돌 검토
  → 설계·위험 판단 (JUDGE)
  → 구현 (BUILD, 직렬)
  → 독립 검증 (구현자와 다른 에이전트)
  → 원장 verification 실행
  → Main이 완료 판정 · 원장/로그/보고서 기록
```

`Explore → Reason → Implement → Verify → Record`. 위험도가 낮으면 단계를 생략할 수 있다.

## 8. 에스컬레이션

역할 전환은 `SCAN → JUDGE → BUILD → VERIFY → JUDGE(final)`의 순서이다.

- 조사 결과끼리 충돌하거나 근거가 파일에 없다
- 원인에 대한 확신이 낮다
- 기존 설계·계약과 충돌한다
- 예상하지 못한 side effect나 보안·데이터 위험을 발견했다
- 테스트는 통과했는데 설계상 의심이 남는다
- 원장의 가정이 실제 코드·운영 상태와 다르다 (**원장 stale 여부를 명시한다**)

### 역할 흐름

```text
SCAN
  ↓
JUDGE
  ↓
BUILD
  ↓
VERIFY
  ↓
JUDGE(final)
```

### Task Risk Floor: JUDGE

- Step 1 조사     → SCAN
- Step 2 위험판정 → JUDGE
- Step 3 구현     → BUILD
- Step 4 검증     → SCAN
- Step 5 최종판정 → JUDGE

**Task Risk Floor는 디에스컬레이션하지 않는다.** 
단, 승인된 계획을 실행하기 위해 step 역할이 **JUDGE → BUILD 또는 SCAN**으로 전환되는 것은 디에스컬레이션이 아니다.

### 8.1 무한 시도 금지 — 중단·보고 게이트 (Stop-and-Report)

**해결이 안 되거나 원인 파악이 안 되거나, 단일 작업이 과도하게 오래 걸리면 무한히 재시도하지 않는다.
시도 한도에 도달하면 즉시 작업을 멈추고 현재 상태를 사용자에게 보고한다.**

- 시도 한도(기본값): **같은 원인 추정에 대한 재검증 3회**, 또는 **단일 작업 누적 30분** 중 먼저 도달하는 것.
- **다른 세션의 진행을 기다리는 시간은 누적 30분에 넣지 않는다** (2026-10-01 신설). 멀티 세션 멤버가 앞 단계를 맡은 다른 참가자의 완료 마커를 기다리는 대기(`todo-multi-session.json` `common.memberMarkerWait`)가 해당한다. 이 한도는 같은 원인을 재검증하는 작업 시도에 대한 것이고, 대기는 시도가 아니다. 무한 대기는 그 절의 중단 조건(대상 세션 이탈·60분 무갱신·리더 판정 대기 또는 blocked·사용자 중단)이 막는다. 대기가 끝나 작업을 재개하면 누적 시간은 재개 시점부터 다시 센다.
- 재현·검증 환경 문제(dev 서버 다운, HMR 상태 리셋, 캐시 손상, 인증 세션 만료 등)로 판정이 흔들리면
  판정을 임의로 반복하지 말고 **환경 복구를 사용자 요청으로 돌린다** — 에이전트가 환경까지 계속 고치는 것은 무한 시도의 대표 발생 지점이다.
- 중단 시 보고에는 ① 확정된 것(근거 포함) ② 미확정·추정(확인 경로 포함) ③ 작업 도중 남긴 임시 변경(디버그 로그, 실험 패치)과 정리 방법 ④ 재개에 필요한 다음 단계를 적는다.
- 중단 후에도 이미 적용한 변경은 그대로 둔다. 검증 없이 숨기거나 되돌리지 말고, 상태를 보고에 명시한다.

## 9. 독립 검증

**구현한 에이전트가 자기 결과를 검증하는 구조에만 의존하지 않는다.** 아래는 독립 리뷰를 필수로 한다.

- 인증·권한 / 코인·결제·경제 / 개인정보·법무 / 데이터 마이그레이션·삭제 / 공개 API 계약 / 공통 컴포넌트·패키지 / WordPress 운영 반영 / 인프라·배포
- **Mechanical verification(SCAN)** — lint, typecheck, test, build, diff 범위 확인, 체크리스트, 잔존 grep
- **Semantic review(JUDGE)** — 설계 계약 준수, 보안, 인증, 데이터 정합성, side effect, migration safety, API backward compatibility

검증 실행과 판정 표기는 `{{AGENT_ROOT}}/rules/reporting.md`를 따른다.
실행하지 못한 항목을 통과로 간주하지 않고, 사유와 함께 남긴다.
구현 완료는 `done`이 아니다. **원장의 `deliverables`와 `verification`을 충족해야 `done`이다.**

## 10. 기록

- 라우팅 근거는 장황하게 쓰지 않는다. 보고서에 **`TASK / step / 역할 / 티어 / 모델 / effort`** 한 줄씩이면 충분하다.
- **로그 JSON에 라우팅용 필드를 새로 만들지 않는다.** 로그 구조는 같은 폴더의 최신 파일을 그대로 따른다
  (`{{AGENT_ROOT}}/rules/reporting.md`). 라우팅 기록은 보고서 본문에 둔다.
- 모델 선택 설명보다 실제 결과와 evidence가 중요하다.

## 11. Agent Teams · Dynamic Workflows

- AMU 원장은 대부분 `dependsOn` 직렬 의존이라 **기본 경로는 Main + Subagents다.**
- Agent Teams(세션 간 협업)는 서로 다른 계층을 동시에 바꾸면서 정보 교환이 필요한 경우에만 검토한다.
  현재 실험 기능이고 기본 비활성이므로, 사용하려면 활성화 여부와 안전 경계를 먼저 사용자와 확정한다.
- Dynamic Workflows는 수십~수백 개 독립 작업을 반복·재현 가능하게 오케스트레이션해야 하거나, 
  turn-by-turn Main 판단보다 script가 실행 계획을 소유하는 편이 명확한 경우에만 사용한다.
- 어떤 방식이든 §4 하드 경계와 §9 독립 검증은 동일하게 적용한다.

## 12. 사용자가 "멀티 세션"을 요청한 경우 — MS-PARALLEL (2026-09-30 신설)

**사용자가 "멀티 세션 방식으로", "여러 세션으로", "멀티 세션으로 진행" 등으로 요청하면 서브에이전트를 띄우지 않는다.**
`.agent/todo-ledgers/tasks/todo-multi-session.json`의 **`MS-PARALLEL`** 규약으로 진행한다.
사용자가 `MS-COLLAB`·`MS-BULK`를 명시하거나 작업 성격이 그 모드의 `applicableTo`에 해당할 때만 다른 모드를 쓴다.

**왜** — 멀티 세션은 사용자가 띄운 **독립 세션**들이 작업을 나눠 하고 서로 교차 검증하는 방식이다.
리더 세션이 서브에이전트로 멤버를 대신 만들면 (1) 조사 전량이 리더 세션의 토큰으로 소모돼 리더가 R4 종합과 다른 작업을 할 여력을 잃고,
(2) 결과가 모두 리더 자신의 산출물이 되어 교차 검증이 성립하지 않는다(`common.oneAgentPerSession`, `MS-PARALLEL.minParticipants`).
실측 사고: 2026-09-30 SSOT-000 — "멀티 세션 방식으로" 요청을 서브에이전트 5개 병렬 실행으로 해석해 사용자가 중단시켰다.

**리더(이 요청을 받은 세션)의 절차**

1. **대상 taskId를 정한다.** 사용자가 원장·taskId를 줬으면 그것을 쓴다. 대응 task가 없으면 리더가 원장을 신설하거나 기존 원장에
   조사 task를 추가한다 — 선례: `todo-jev-decision-fabric.json` JEV-000, `todo-ai-model-ssot.json` SSOT-000(조사·로드맵 확정 task, `provisional: true`).
   원장 쓰기는 §4에 따라 리더(Main)만 한다.
2. `todo-multi-session.json`의 `howToStart`·`common`·`MS-PARALLEL.prompt` R0를 **그대로** 수행한다 — 워크스페이스 루트 확정, 원장 최상위 `slug` 필드로 사이클 경로 계산,
   `mkdir` 원자성으로 리더 선출, 참가 등록, `ROUND.md` 작성(단위·확정 설계·검증 배정·락·금지·규모 산정·걸리는 규칙 원문).
3. **R0가 끝나면 멈추고 사용자에게 보고한다.** 보고 첫 줄에 필요 세션 수, 본문에 단위 배정표, 그리고 멤버 세션에 줄 한 줄 지시
   (`<원장 경로>의 <taskId> 작업을 진행해줘`)를 적는다. 마지막 줄은 `common.reportSignature` 형식이다.
4. 리더는 단위를 구현·조사하지 않는다. 사용자가 "작업자들이 끝났다"고 알리면 R2 최후 검토(검토 없는 산출물이 있으면) → **R4 종합**
   (명부·쓰기 경계·검증 합산표·원장·보고서·로그·완료 마커)을 수행한다. R3를 마치지 못한 단위는 통과로 간주하지 않고,
   지적 사항을 리더가 종합 보고서에서 직접 대조·보충하되 멤버의 산출물 파일은 고치지 않는다.

**하지 않는 것**

- 멤버 역할을 Agent/Task 도구의 서브에이전트로 채우기. 읽기 전용 탐색 위임도 **리더 R0 판단에 필요한 최소 범위**를 넘지 않는다.
- 참가자가 리더뿐인데 R1 시작하기(`MS-PARALLEL.minParticipants`).
- 사용자에게 세션 수·라운드를 되묻기(`howToStart.note`) — 규모 산정 결과를 알리고 멈추는 것은 되묻기가 아니다.
