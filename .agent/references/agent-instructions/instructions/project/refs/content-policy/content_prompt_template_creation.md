# Content Prompt Template Creation Rules (콘텐츠 프롬프트 템플릿 생성)

## 목표

1. 텍스트 콘텐츠 생성용 프롬프트(편집자형, 칼럼니스트형, 사고 공식 등)를 분석하여 gen-studio 서비스의 `ContentPromptSchema`에 호환되는 재사용 가능한 템플릿으로 변환
2. 팀 구성 요청 시 시나리오 플래너, 카피라이터, SEO 에디터, 휴머나이저로 구성된 4명의 팀메이트를 만들어 각 역할간 협업으로 최고의 결과물 생성

## 소재 라우팅 (착수 게이트 직전)

소비 원장은 `.agent/content/ai-prompts/content_templates/references/content_template_reference.md`다.
폴더 자료를 먼저 소진하고 URL 자료로 넘어가며, 한 사이클에 1건을 소비한다.

**소재가 콘텐츠 생성 프롬프트와 무관하면 템플릿을 만들지 않는다.** 해당 링크를 아래 문서로 옮기고
원장에서는 제거하며, 판정 근거를 한 줄로 함께 적는다.

| 소재 성격 | 옮길 문서 |
| --- | --- |
| 이미지 생성 | `.agent/content/ai-prompts/image_templates/references/image_template_reference.md` |
| 영상 제작 | `.agent/content/ai-prompts/생성형_AI_동영상_테스트.md` |
| 기타(디자인·툴·그 외) | `.agent/content/ai-prompts/생성형_AI_기타.md` |

- 포스트가 아닌 URL(스레드 홈 피드 `threads.com/?xmt=`, 검색 URL)과 삭제·비공개로 접근 불가한 포스트는
  라우팅 대상이 아니라 **제거 대상**이다. 사유를 보고에 남긴다.
- 라우팅은 4축 판정보다 **먼저** 한다. 콘텐츠 소재가 아닌 것을 콘텐츠 템플릿 후보로 놓고 중복 검사를 돌리지 않는다.
- **한 폴더 = 한 템플릿 작업 단위다.** 여러 프롬프트가 든 폴더는 개별 프롬프트를 그대로 템플릿으로 옮기지 말고,
  공통 역할·입력 변수·출력 구조를 뽑아 하나의 템플릿으로 설계한다. 개별 프롬프트는 그 템플릿의
  옵션 값 또는 조건 블록 후보로 쓴다. 폴더 하나에서 템플릿을 여러 개 만들어야 한다고 판단되면
  4축 판정으로 서로 다른 템플릿인지 먼저 확인한다.

## 착수 게이트: 중복·유사 템플릿 선점 검사 (필수)

템플릿 수가 늘면서 **같은 개념이 key만 다르게 재등록되는 사고**가 누적되고 있다.
**신규 등록은 기본값이 아니다.** 아래 검사에서 중복·유사로 판정되면 신규 생성 대신 **기존 템플릿 개선(갱신)**으로 전환한다.

### 1단계 — 후보 조회 (소재 분석 직후, 등록 전)

`genstudio` MCP로 아래를 모두 조회한다. key 문자열 일치 검사만으로는 개념 중복을 잡을 수 없다.

```text
list_prompts({ promptType: "content", q: <핵심 개념어>, limit: 100 })   # 한글/영어 키워드마다 반복
list_prompts({ promptType: "content", category: <대표카테고리>, limit: 100 })  # 대표카테고리마다 반복
get_prompt_template({ templateKey: <상위 후보>, promptType: "content" })       # 후보 3~5건 본문 대조
```

- 검색어는 제목 문구가 아니라 **개념어**로 만든다(예: `요약`, `summary`, `아이디어`, `사고법`, `카피`, `copywriting`).
- 조회에 실패하면 판정을 추정으로 대체하지 않고 **등록을 중단하고 `blocked`로 보고**한다(fail-closed).

### 2단계 — 정체성 4축 판정

| 축 | 콘텐츠 템플릿의 판정 기준 |
| --- | --- |
| ① 산출물 유형 | 기사/블로그 · 카피/광고문구 · 아이디어/발상 · 요약/정리 · 분석/보고서 · 기획/전략 |
| ② 역할·사고 프레임 | 편집자형 · 칼럼니스트형 · 카피라이터형 · 사고 공식형 · 콘텐츠 전략형 |
| ③ 채널 | `defaultParams.platform` (`naver-blog`/`linkedin`/`threads`/`wp-blog`/`general`) |
| ④ 출력 구조·포맷 | `outputFormat`과 구조 지시(섹션 구성, 표/다이어그램 유무, 분량 규격) |

- **3축 이상 일치 → 중복.** 신규 생성 금지. 기존 템플릿 개선으로 전환한다.
- **2축 일치 → 유사.** 기존 템플릿에 옵션·조건 블록으로 **흡수하는 것이 1순위**다. 아래 분리 허용 기준을 충족할 때만 신규 생성한다.
- **1축 이하 → 신규 생성.**

### 3단계 — 분리 허용 기준 (유사인데 신규를 만들어도 되는 경우)

하나 이상 충족해야 하며, 충족한 항목을 **판정 근거로 기록**한다.

- 흡수하면 고정 설정(역할/구조/톤/품질기준)이 서로 모순되어 조건 블록 없이 성립하지 않고, 필요한 조건 블록이 12개를 넘는다
- 흡수하면 한 필드의 Select 옵션이 24개를 넘어 선택 피로가 생긴다(콘텐츠 템플릿의 권장 상한은 2~8개)
- `defaultParams`의 지배값(`platform`·`outputFormat`)이 서로 달라 기본값 하나로 수렴되지 않는다
- 필수 자유 입력 변수의 성격이 달라(예: `원문 텍스트` vs `주제 한 줄`) 한 템플릿에서 동시에 강제할 수 없다
- `accessLevel` 또는 운영 그룹이 달라 노출 대상이 분리되어야 한다

### 4단계 — 기존 템플릿 개선(갱신) 절차

1. `get_prompt_template`으로 현재 `templateText`·`defaultParams`·`categories`·`tags`를 **전량 확보**한다.
2. 새 소재에서 **추가할 가치만** 추출한다 — 새 옵션 값, 새 조건 블록, 더 정확한 역할·구조 서술, 보강 키워드.
3. 병합은 **가산만 허용**한다.
   - `key` 변경 금지 (rename 미지원)
   - 기존 변수명·옵션 라벨의 삭제·개명 금지 — 저장된 생성 이력·딥링크·조건 블록 참조가 깨진다. 불가피하면 사용자 승인 후 진행
   - 기존 고정 설정을 덮어쓰지 말고, 달라지는 지시는 **조건 블록으로 추가**한다
   - `categories`·`tags`는 합집합으로 만들고 상한(대표카테고리 2~4개, 키워드 각 10개) 초과분은 대표성이 낮은 값부터 제거
   - `usageTip`은 140자 상한 안에서 갱신
4. `upsert_content_prompt_template`을 `strictNew=false`, `version = 기존 version + 1`로 호출한다. **개선 목적의 `strictNew=false`는 이 절차를 거친 경우에만 허용**한다.
5. `get_prompt_template`으로 재조회해 병합 결과와 한글 표기를 검수한다(`{{AGENT_ROOT}}/rules/text-encoding-integrity.md`).
6. 템플릿 문서는 **기존 key와 같은 파일명으로 `completed/`의 문서를 갱신**하고, `new/`에 같은 개념의 새 문서를 남기지 않는다.
7. `content-ledger.jsonl`에 갱신 행을 append한다 — `type: "content-template"`, `status: "updated"`, `slug: <기존 key>`, `dedupeKey: "topic:<기존 key>"`, `source.summary`에 흡수한 소재 ref와 일치 축을 남긴다. 기존 행은 수정하지 않는다.

## 분석 절차

1. **프롬프트 구조 분석**: 역할 정의, 입력 변수, 출력 형식, 제약 조건, 품질 기준을 식별
2. **변수 분리**: 사용자가 매번 달리 입력해야 하는 요소를 `{변수명::옵션1|옵션2|...}` 형태로 추출
  - 선택 자유 입력: `{변수명::placeholder}`
  - 필수 자유 입력: `{변수명*::placeholder}`
  - 선택 Select: `{변수명::옵션1|옵션2|옵션3}`
  - 필수 Select: `{변수명*::옵션1|옵션2|옵션3}`
3. **조건 분기 분리**: 선택값에 따라 달라지는 역할·구조·톤·품질기준은 `{#if field == "value"}...{/if}` 블록으로 추출
4. **역할/컨텍스트 고정**: 프롬프트의 역할 정의, 톤, 구조 지시 등 매번 동일한 부분은 templateText에 고정
5. **카테고리/태그 분류**: 용도별 분류 (글쓰기, 마케팅, 사고법, 분석, 요약 등)
6. **플랫폼/언어/길이 기본값 설정**: defaultParams 구성

## 출력 템플릿 구조 (필수)

아래 구조를 반드시 준수한다:

> 작성된 템플릿을 gen-studio DB(`content_prompts` 컬렉션)에 등록할 때는 `genstudio` MCP의 `upsert_content_prompt_template` 도구를 사용한다. 마크다운 → 페이로드 매핑 및 필수 검증 절차는 `{{AGENT_ROOT}}/refs/genstudio-prompt-registration-guide.md`를, 도구 사용 일반 규칙은 `{{AGENT_ROOT}}/skills/amu-custom-mcp/SKILL.md`를 우선 참조. 1차 등록은 항상 `strictNew=true`.

```
# {프롬프트의 용도를 한 줄로 설명하는 제목}

{english-kebab-case-key}

## 용도:

{어떤 상황에서 이 프롬프트를 사용하는지 안내}

## 대표카테고리:

{쉼표 구분 2~4개}

## 키워드:

{한글 키워드 최대 10개}, {영어 키워드 최대 10개}

## 활용팁: 

{140자 이내 최적 활용 안내}

## 기본설정:

- `platform`: 해당 템플릿을 가장 잘 활용하는 채널 (`naver-blog|linkedin|threads|wp-blog|general`)
- `language`: 출력 언어 (`ko` 기본)
- `length`: 채널/포맷별 분량 (`threads: 2-4문장` | `linkedin: 800-1200자` | `blog: 1500-2500자` | `instagram: 3-5문장` | 기타). 해시태그는 별도 입력 필드에 저장하고 본문에 포함하지 않는다.
- `outputFormat`: 출력 포맷 (`markdown/mermaid` | `json`)
  - `markdown/mermaid`: Markdown 문서를 생성하며 필요한 경우 fenced code block의 `mermaid` 문법을 포함할 수 있음
  - `json`: 구조화된 JSON 문서를 생성

## 템플릿:

역할:
AI에게 부여할 역할/페르소나 고정 설정. 동적 요소는 {주제::옵션1|...} | {주제::설명} 형태

구조:
출력물의 구조/형식 고정 설정. 동적 요소는 {주제::옵션1|...} | {주제::설명} 형태

톤:
문체/어조 고정 설정. 동적 요소는 {주제::옵션1|...} | {주제::설명} 형태

품질기준:
출력 품질을 보장하기 위한 필수 조건. 동적 요소는 {주제::옵션1|...} | {주제::설명} 형태

{기타}:
기타 콘텐츠 생성 템플릿을 위한 추가적인 설정들 추가 가능
```

## 템플릿 설계 원칙

> 아래 4개 라벨은 위 출력 템플릿 구조의 `## 템플릿:` 하위 블록에 그대로 채워 넣는다. 각 라벨의 채움 기준은 다음과 같다.

- 역할: AI에게 부여할 역할/페르소나 고정 설정
- 구조: 출력물의 구조/형식 고정 설정.
- 톤: 문체/어조 고정 설정. **소셜 채널(naver-blog/linkedin/threads/instagram) 대상 템플릿은 친근한 존대어(해요체/습니다체)를 고정값으로 명시**하고, 반말·평어 종결을 쓰지 않음.
- 품질기준: 출력 품질을 보장하기 위한 필수 조건
- 동적 요소는 {주제::옵션1, 옵션2, ...} 또는 {주제::placeholder} 형태의 변수로 설정

## 변수 설계 원칙

- **고정 vs 동적 판단 기준**: 프롬프트의 "뼈대"(역할, 구조, 톤)는 고정, "살"(주제, 입력 텍스트, 타깃)은 동적
- **변수명 규칙**: 라벨은 한글 또는 영어 snake_case 사용
  - 예: `{CTA_문구::사용자의 행동을 유도할 내용을 입력하세요.}`, `{톤::전문가|친근|도발적}`
- **옵션 수 제한**: 선택 변수는 2~8개 옵션 권장 (너무 많으면 사용성 저하). 12개 이상이면 생성 화면이 검색형 셀렉트박스 시트로 자동 전환되며 전체 옵션 수가 함께 표시됨
- **확장 옵션 토큰**: Select 옵션은 `;`로 분절해 `라벨; 설명; 프롬프트` 형태로 화면 라벨과 실제 치환 문장을 분리할 수 있음
  - `옵션값`(구분자 없음): 라벨 = 치환 문장. `normalizeLabel()`이 적용되어 `-`/`_`가 공백이 되고 단어 첫 글자가 대문자로 바뀜
  - `라벨; 프롬프트` / `라벨; 설명; 프롬프트`: 프롬프트 분절을 **원문 그대로** 치환 (프롬프트 안의 `;`는 보존)
  - 옵션 값이 한 문장 이상의 지시문이거나 영문 표기·대소문자가 의미를 갖는 경우에만 사용하고, `친근`·`전문` 같은 한글 단문 옵션은 기본형 유지
  - 옵션 값 안에는 `|` `{` `}` 를 넣지 않음(변수 토큰 문법과 충돌)
  - 확장 토큰 필드를 조건 블록에서 참조할 때는 **라벨로 비교**: `{#if 톤 == "공감"}`
- **필수 자유 입력 변수**: 최소 1개 이상이며 `{변수명*::placeholder}`로 명시
- **존대어 레지스터 고정**: 소셜 채널 대상 템플릿에서 `{톤::}` 변수는 "존대어 안에서의 분위기 차이"(예: `{톤::친근|전문|공감}`)만 표현하고, 높임 레벨 자체를 바꾸는 옵션(반말 유발)은 두지 않음.

## 조건 블록 설계 원칙

- 조건 블록은 선택값에 따라 최종 프롬프트에 포함할 문장을 고르는 용도로만 사용.
- 허용 문법:
  ```text
  {#if field == "value"}
  선택값이 value일 때만 포함할 콘텐츠 생성 지시문
  {/if}
  ```
- `else`, `elseif`, 중첩 조건, `and`, `or`, 정규식 조건은 사용하지 않음.
- 여러 선택값에 각각 다른 지시문이 필요하면 독립적인 if 블록을 나란히 작성.
- 조건에 사용하는 `field`는 반드시 같은 템플릿 안에 정의된 입력 변수여야 함.
- 콘텐츠 템플릿에서는 채널, 독자 수준, 글 형식, CTA 강도, 출력 포맷, 금지 표현, 검증 기준처럼 선택값에 따라 문체나 구조가 달라지는 영역에만 조건 블록을 사용.

## 품질 기준

### 기사·블로그 산출물용 추가 기준

`산출물 유형`이 기사/블로그이거나 Magazine Experience의 콘텐츠 생성 모듈로 연결될 때만 아래를 적용한다.

- 템플릿이 `primary question → expected answer → evidence → tension → reader choice/comparison → application → next question`을 구조화할 수 있어야 한다.
- 질문만 강하고 답·근거가 약한 결과를 만들지 않도록 `Hook Strength ≤ Answer Strength`를 품질 기준에 포함한다.
- 일반 요약·카피·JSON·고객 응대 템플릿에는 이 기사 서사 구조를 강제하지 않는다.

- 착수 게이트의 선점 검사를 수행했고, 조회한 후보 목록과 4축 판정 결과를 근거로 남겼는지 확인
- 유사 판정인데 신규로 만든 경우 분리 허용 기준 중 어떤 항목을 충족했는지 명시했는지 확인
- 개선(갱신)한 경우 기존 변수·옵션이 하나도 삭제·개명되지 않았고 `version`이 1 증가했는지 확인
- 변환된 템플릿으로 실제 콘텐츠를 생성했을 때 원본 프롬프트와 동등한 품질이 나와야 함
- 역할/구조/톤/품질기준 4개 섹션 모두 충분히 상세하게 기술 (각 최소 2줄 이상)
- 자유 입력 변수가 비어있을 때 동작하지 않도록 필수 표시

## gen-studio 호환성 규칙

- `key`는 영문 kebab-case, 고유값 (기존 image_prompts 컬렉션의 key와 중복 불가)
- `templateText`는 렌더링 시 `{변수명::옵션}` 입력 문법과 `{#if field == "value"}...{/if}` 조건 블록 문법이 함께 해석됨
- `categories`는 기존 gen-studio UI의 필터와 호환되는 값 사용
- `defaultParams.platform`은 gen-studio ContentPromptSchema의 platform 필드와 매핑
- `defaultParams.outputFormat`은 `markdown/mermaid` 또는 `json`만 사용
- Mermaid 다이어그램은 `markdown/mermaid` 문서 안의 fenced code block으로 표현하며 별도 `mermaid` 출력 포맷으로 분리하지 않음

## DB 등록 절차

- **등록 전 착수 게이트의 선점 검사를 먼저 통과**한다. 중복·유사 판정이면 신규 등록이 아니라 개선(갱신) 경로로 진행
- 작성된 템플릿을 `content_prompts` 컬렉션에 등록할 때는 `genstudio` MCP의 `upsert_content_prompt_template` 도구를 사용
- 마크다운 → 페이로드 매핑과 검증 절차는 `{{AGENT_ROOT}}/refs/genstudio-prompt-registration-guide.md` 우선 참조
- MCP 도구 사용 일반 규칙(인증·rate-limit·에러 매트릭스)은 `{{AGENT_ROOT}}/skills/amu-custom-mcp/SKILL.md` 우선 참조
- 신규 등록은 항상 `strictNew=true`로 호출하여 데이터 덮어쓰기 방지
- `strictNew=false`는 착수 게이트 4단계의 개선 절차를 거친 **의도된 갱신에만** 사용

## 금지 사항

- 착수 게이트의 선점 검사 없이 새 key를 등록하는 것
- 같은 개념을 `-v2`, `-2`, `-new`, `-final` 같은 접미사를 붙인 새 key로 재등록하는 것 (버전은 `version` 필드로 관리)
- 중복 판정을 피하려고 제목·대표카테고리·키워드만 바꿔 등록하는 것
- 기존 템플릿의 변수·옵션을 삭제하거나 이름을 바꿔 갱신하는 것
- `CONFLICT`(409)를 만났을 때 key를 변형해 우회 등록하는 것
- 분석 없이 일반적인 프롬프트 복사 붙여넣기
- 원본 프롬프트의 핵심 구조를 훼손하는 과도한 단순화
- 변수를 고정값으로 하드코딩 (사용자 입력이 필요한 부분)
- 템플릿 구조 항목 누락
- gen-studio 변수 문법(`{key::options}`)과 다른 형식 사용
- 조건 분기에 `else`, `elseif`, 중첩 조건, 복합 조건을 사용하는 것
- 존재하지 않는 변수를 조건 블록에서 참조하는 것
- 조건 설명(`A인 경우:` 등)을 모델에 전달되는 최종 지시문으로 남기는 것
